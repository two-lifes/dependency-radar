# Рабочий цикл разработки

Правила для Codex и Claude Code. Цель — закончить согласованную задачу небольшим проверяемым изменением, без полного аудита проекта после каждого пункта.

## Задачи и этапы

- Задача — номер в [plan.md](plan.md); этап разработки — раздел **A–F** этого плана.
- MVP / 1.1 / 1.2 из spec определяют продуктовый объём, но не частоту проверок.
- Источник правил проверки — [AGENTS.md](../AGENTS.md#verification-cadence-and-development-speed). Полные прогоны и браузерная проверка разрешены только при завершении этапа или по прямому запросу пользователя.

## Цикл одной задачи

1. Найти первый незавершённый пункт через `next-task`. Читать только связанные требования и участки кода, а не весь каталог docs и весь проект.
2. Для нетривиальной задачи дать короткий план: изменения, существенные крайние случаи, целевые тесты. Согласовать его один раз; не запрашивать повторное разрешение на обычные шаги внутри согласованного объёма.
3. Реализовать только этот пункт. Новую логику и исправления ошибок покрыть тестами; для чистой логики анализа тесты писать первыми. Не добавлять рефакторинг и исправления сторонних проблем.
4. Проверить diff, запустить ESLint изменённых файлов и только новые/затронутые unit/RTL-тесты. При изменении TypeScript выполнить typecheck один раз. Для документации достаточно diff, ссылок и согласованности.
5. Остановиться после успешных целевых проверок. Полные тесты, build, БД, e2e, браузер и скриншоты на этом шаге не запускать. Не разворачивать стенд ради закрытия пункта.
6. Кратко сообщить: что изменено; что фактически проверено; что отложено до конца этапа или заблокировано. Не представлять отложенные проверки как успешные. Существенные отложенные сценарии записать в соответствующий раздел plan.md.
7. Коммит, push и отметку пункта делать только по запросу или подтверждению пользователя. Они сами по себе не запускают новый цикл проверок.

## Завершение этапа A–F

После реализации последнего незавершённого пункта раздела:

1. Один раз выполнить полный lint, typecheck, unit/RTL и production build. Не повторять уже выполненную на том же коде проверку без причины.
2. Выполнить применимые к этапу PostgreSQL-интеграционные тесты и e2e, включая накопленные отложенные сценарии. Внешние API в e2e подменять существующим MSW-стендом; реальные запросы нужны только там, где это прямо требует приёмка.
3. Для этапа с UI открыть изменённые экраны через Playwright MCP, сверить с screens.md и wireframes.png, сделать скриншоты в обеих темах на 1440px и 390px. Дополнительные размеры — только по требованиям этапа; для пункта 28 также 375px. Не переснимать все экраны проекта без необходимости.
4. После сбоя исправить причину и повторить провалившиеся и непосредственно затронутые проверки. Успешный прогон не повторять только ради финального ответа или коммита.
5. Сообщить результаты и оставшиеся ограничения. Этап не считать проверенным, если обязательная проверка не выполнена. Миграции и необратимые действия требуют прежнего согласования; закрытие этапа не даёт разрешения менять рабочую БД.

Текущий этап F заканчивается приёмкой в пункте 29. После пункта 28 полного прогона нет. Настройки CI не меняются; автоматический CI не требует дублировать его локально.

## Как не затягивать работу

- Использовать существующие компоненты, зависимости и тестовый стенд; не создавать отдельную инфраструктуру ради удобства проверки.
- Не запускать Docker, установку браузеров, вспомогательные серверы или настройку БД после каждого пункта. Если целевая проверка недоступна, назвать блокер и отложенную проверку; не тратить сессию на обходные стенды.
- До запуска проверки определить, какой конкретный риск изменения она проверяет. Если связи нет — не запускать.
- Не повторять чтение документации, поиск API и успешные проверки без новых данных. Для используемого внешнего API достаточно целевой проверки актуальной документации; повторно проверять весь стек не нужно.
- После двух неудачных подходов к одной проблеме остановиться, описать наблюдения и предложить варианты, как требует правило проекта.
- Не очищать контекст принудительно после каждого пункта: продолжать текущую сессию, пока в ней удобно работать; при смене сессии опираться на plan.md и decisions.md.
- Сохранять требования к доступности, состояниям интерфейса и тестам. Меняется частота тяжёлой проверки, а не требования к результату.
