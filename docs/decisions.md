# Решения по стеку (docs/decisions.md)

> Для задачи 26.2 целевые правила гостевого доступа задаёт [решение 53](#decision-53). Упоминания действующего демо в более ранних решениях — история; они не предписывают сохранять демо-сценарий после 26.2. Защита magic link и старых демо-сессий сохраняется.

Каждый пункт — готовый ответ на вопрос «почему вы выбрали X?» на собеседовании. Новые решения дописывайте в том же формате.

---

### 1. Next.js App Router
**Контекст:** нужны лендинг с хорошим SEO и быстрым первым экраном, приложение за авторизацией и серверная часть для обращения к внешним API.
**Решение:** Next.js App Router.
**Почему:** фронт и сервер в одном проекте, Server Components отдают данные без лишнего JS на клиенте, Server Actions подходят для мутаций, route handlers — для стриминга прогресса. Это самый востребованный стек в вакансиях с React.
**Альтернативы:** Vite SPA + отдельный бэкенд (два деплоя, хуже SEO лендинга), Remix / React Router 7 (тоже подходит, но меньше спрос в вакансиях).

### 2. PostgreSQL (Neon) + Drizzle ORM
**Контекст:** данные реляционные: пользователи, команды, проекты, проверки, пакеты, кэш внешних ответов.
**Решение:** Postgres на Neon, Drizzle как ORM.
**Почему:** у Neon есть бесплатный тариф, он serverless и интегрируется с Vercel. Drizzle полностью типизирован, запросы близки к SQL (видно, что выполняется), он лёгкий и не требует отдельной генерации клиента.
**Альтернативы:** Prisma (тяжелее, но популярнее), Supabase (сразу БД и авторизация, но сильнее привязывает к платформе).

### 3. Better Auth
**Контекст:** нужны вход через GitHub и по ссылке на email, а позже команды и роли.
**Решение:** Better Auth.
**Почему:** TypeScript-first, работает с Drizzle, есть плагины для magic link и организаций (команды и роли). Сессии хранятся в нашей БД, без внешнего сервиса.
**Альтернативы:** Auth.js (с 2025 года развивается командой Better Auth), Clerk (быстро, но платный сервис и чужой UI).
**Проверить при старте:** актуальность плагинов magic link и organization в документации Better Auth.

### 4. Кэш внешних API в Postgres
**Контекст:** у GitHub API есть лимит запросов, а проверка проекта делает сотни запросов.
**Решение:** таблица кэша (ключ, ответ, срок жизни) в той же БД, TTL 1 час, ограниченная параллельность запросов.
**Почему:** не нужен отдельный сервис (Redis), повторная проверка выполняется мгновенно, лимиты не исчерпываются.
**Альтернативы:** Redis (Upstash) — быстрее, но это ещё один сервис; кэш Next.js `fetch` — менее прозрачный и плохо контролируемый.

### 5. Прогресс проверки через SSE
**Контекст:** проверка занимает секунды, и пользователь должен видеть прогресс и частичные результаты (ТЗ 6.2).
**Решение:** Server-Sent Events из route handler.
**Почему:** поток идёт в одну сторону (сервер → клиент), SSE проще WebSocket, работает по обычному HTTP и переподключается сам.
**Альтернативы:** polling (проще, но с задержкой и лишними запросами), WebSocket (избыточен для однонаправленного потока).

### 6. Состояние фильтров в URL (nuqs)
**Контекст:** ТЗ требует, чтобы ссылка открывала ту же выборку таблицы.
**Решение:** фильтры, сортировка, поиск и открытый пакет хранятся в search params через nuqs.
**Почему:** типизированные search params, работает и в Server, и в Client Components, состояние можно передать ссылкой.

### 7. TanStack Table + TanStack Virtual
**Контекст:** таблица с 500+ строками, сортировкой, фильтрами и массовым выделением.
**Решение:** headless-таблица TanStack и виртуализация строк.
**Почему:** логика таблицы без навязанной вёрстки (разметку и доступность контролируем сами), виртуализация держит отзывчивость при больших списках.

### 8. Zod везде на границах
**Решение:** одна схема Zod для формы, Server Action и ответов внешних API.
**Почему:** внешним данным нельзя доверять. Валидация на границе даёт типы и понятные ошибки, а не падение глубоко в коде.

### 9. Чистая логика анализа отдельно от I/O
**Решение:** расчёт отставания, оценки здоровья, поиск breaking changes и построение плана — чистые функции в `src/server/analysis`.
**Почему:** их легко покрыть unit-тестами без сети и БД. Это самая важная логика продукта.

### 10. Тесты: Vitest + Testing Library + MSW + Playwright
**Почему:** Vitest быстрый и совместим с API Jest. Testing Library тестирует поведение, а не реализацию. MSW подменяет внешние API на уровне сети, поэтому тесты не зависят от npm и GitHub. Playwright прогоняет ключевые сценарии ТЗ в настоящем браузере в CI.

### 11. Vercel + GitHub Actions, задачи по расписанию через GitHub Actions

> **Уточнение для [решения 53](#decision-53), реализовано в 26.2:** В задаче 26.2 отменяется только автоматический сброс демо; способ запуска cron, защита и очистка истёкших отчётов сохраняются.

**Контекст:** уже в MVP нужна ежедневная задача: физически удалить гостевые отчёты старше 7 дней и сбросить демо-аккаунт. В 1.2 добавятся регулярные проверки проектов.
**Решение:** деплой на Vercel (превью на каждый PR, бесплатный тариф). CI в GitHub Actions проверяет lint, типы, unit- и e2e-тесты до мержа. Задачи по расписанию запускает workflow GitHub Actions (`schedule`), который вызывает route handler `/api/cron/daily`, защищённый секретом в заголовке.
**Почему:** не зависим от лимитов Vercel Cron на бесплатном тарифе, расписание и логи запусков лежат в репозитории рядом с CI. Истечение гостевого отчёта проверяется при каждом открытии, поэтому корректность не зависит от того, отработала ли задача: она только чистит данные. В 1.2 тот же механизм запускает регулярные проверки.
**Альтернативы:** Vercel Cron (ограничен на бесплатном тарифе), внешний cron-сервис (ещё одна зависимость).
**Проверено при старте:** лимит длительности функции Vercel достаточен, проверка остаётся внутри SSE route handler (раздел 16).

### 12. Geist + дизайн-токены в теме Tailwind
**Контекст:** нужен строгий чёткий шрифт уровня SF Pro и единый стиль на всех экранах, которые пишутся с помощью AI-агента.
**Решение:** Geist Sans / Geist Mono (пакет `geist`) и все цвета, размеры и скругления как токены в `docs/design/theme.css` (Tailwind v4, имена переменных как в shadcn/ui).
**Почему:** SF Pro по лицензии Apple нельзя встраивать в сайт. Geist бесплатный (OFL), хорошо читается в мелких размерах, моноширинная пара подходит для версий пакетов. Токены не дают стилю расползаться: компоненты используют `bg-card`, `text-danger`, а не случайные hex-цвета; тёмная и светлая тема переключаются одним классом.
**Альтернативы:** Inter (более нейтральный), отдельный дизайн-файл в Figma (точнее, но его нельзя проверить автоматически и легко рассинхронизировать с кодом).

### 13. Тема: свой inline-скрипт в `<head>`
**Контекст:** тема по умолчанию System, переключение классом `.dark` на `<html>`, без мигания при загрузке (стайлгайд, раздел 8).
**Решение:** скрипт из `src/lib/theme.ts` вставляется в `<head>` корневого layout и до отрисовки ставит `.dark` и `color-scheme` по значению `theme` в `localStorage` (`light` / `dark` / `system`). При System скрипт следит за сменой системной темы. Если хранилище недоступно или значение неизвестно, используется System.
**Почему:** это около 20 строк без зависимостей. Тест выполняет ту же строку, которая уходит в браузер, поэтому тест и код не расходятся.
**Альтернативы:** `next-themes` (готовое решение, но ещё одна зависимость вне стека ради одной функции).

### 14. Версии инструментов: TypeScript 5 и ESLint 9
**Контекст:** при старте уже вышли TypeScript 7 и ESLint 10.
**Решение:** TypeScript `^5`, ESLint `^9`.
**Почему:** так ставит create-next-app 16.4. Плагины внутри `eslint-config-next` (react, jsx-a11y, import) объявляют совместимость только до ESLint 9, а совместимость TypeScript 7 с typescript-eslint не проверена.
**Альтернативы:** последние мажорные версии — получаем предупреждения о несовместимых зависимостях и риск сломанного lint.

### 15. Дополнительные dev-зависимости: `eslint-config-prettier`, `@testing-library/jest-dom`
**Контекст:** CLAUDE.md разрешает только зависимости из списка стека.
**Решение:** добавлены две dev-зависимости, обе одобрены автором.
**Почему:** `eslint-config-prettier` отключает правила ESLint, которые спорят с Prettier, иначе `lint` и `format` противоречат друг другу. `@testing-library/jest-dom` даёт матчеры `toBeInTheDocument`, `toHaveClass`, `toHaveAttribute` для проверок доступности в RTL-тестах.
**Альтернативы:** ручные проверки через `expect(el.getAttribute(...))` (многословнее и хуже сообщения об ошибках).


### 16. Длительность проверки на Vercel: проверка внутри SSE route handler
**Контекст:** проверка выполняется в SSE route handler (раздел 5), а в лимит длительности функции Vercel входит и время стриминга ответа. По таймауту Vercel обрывает запрос с 504 `FUNCTION_INVOCATION_TIMEOUT`. Нужно понять, укладывается ли проверка 300 пакетов в этот лимит.
**Факты (документация Vercel, fluid compute включён по умолчанию):** на Hobby 300 с по умолчанию и максимум. На Pro по умолчанию тоже 300 с, но можно поднять до 800 с.
**Оценка:** ТЗ требует, чтобы 100 пакетов проверялись не дольше 30 с, то есть 300 пакетов (максимум) — около 90 с без кэша. Запас примерно в 3 раза.
**Решение:** проверка идёт внутри SSE route handler, у handler `export const maxDuration = 300`. Каждый результат пакета сразу пишется в БД, поэтому при обрыве (таймаут, закрытая вкладка) Resume доделывает только непроверенные пакеты.
**Почему:** один запрос вместо двух и нет механизма фонового запуска и опроса прогресса. Худший случай — таймаут — уже покрыт Resume.
**Альтернативы:** проверка отдельным запросом с прогрессом в БД, SSE только читает (сложнее, нужен фоновый запуск); Vercel Workflows (ещё одна платформенная зависимость). Переходим на них, если реальный замер 300 пакетов (задача 29) окажется дольше 200 с.

### 17. UI-примитивы: `radix-ui` одним пакетом, clsx + tailwind-merge + cva
**Контекст:** нужны доступные Dialog, Popover, DropdownMenu, Tooltip, Tabs и Toast, а также единый способ описывать варианты компонентов (Button, Badge) и объединять классы.
**Решение:** пакет `radix-ui` целиком, а не `@radix-ui/react-*` по отдельности. Варианты описываются через `class-variance-authority`, классы объединяются функцией `cn` из `src/lib/cn.ts` (`clsx` + `tailwind-merge`). Все три зависимости одобрены автором.
**Почему:** документация Radix рекомендует единый пакет: он поддерживает tree-shaking и исключает расхождение версий отдельных примитивов. С tailwind-merge `className` снаружи корректно перебивает классы варианта (например, `h-8` вместо `h-9`). tailwind-merge знает только тему по умолчанию, поэтому в `cn` ему передаются наши размеры текста (`2xs`, `md`, `hero`) и `shadow-overlay`. Без этого `text-hero` считается цветом, и рядом с `text-sm` остаются оба класса. Этот список нужно поддерживать вместе с `globals.css`.
**Альтернативы:** своя `cn` без зависимостей (тогда конфликтующие классы из `className` не перебиваются); отдельные пакеты `@radix-ui/react-*`.

### 18. Разбор `package.json`: какие зависимости считаются и как возвращаются ошибки
**Контекст:** в таблице у пакета только два типа (основная или dev), а сообщения об ошибках ввода (screens 5.1) должны быть одинаковыми для Paste, Upload и GitHub URL.
**Решение:** `parseManifest` (`src/server/analysis/parse-manifest.ts`) учитывает только `dependencies` и `devDependencies`. Пакет из обоих разделов считается один раз, как основной. Ошибки возвращаются кодами с данными (`line`, `max`, `maxBytes`, `format`) без текста, а тексты лежат в `src/features/check/copy.ts`: там тип требует текст для каждого кода. JSON, который не похож на `package.json` (корень не объект, версия не строка), получает отдельное сообщение «This doesn't look like a valid package.json.» (spec 8). Номер строки невалидного JSON берётся из сообщения V8 (`line N` или `position N`); если его нет, строка не показывается.
**Почему:** npm сам ставит версию из `dependencies`, если пакет указан в обоих разделах. Коды вместо текста оставляют логику чистой и позволяют позже перевести интерфейс (spec 9).
**Альтернативы:** учитывать `peerDependencies` и `optionalDependencies` (в таблице для них нет типа); бросать исключения с текстом (логика смешивается с копирайтом).

### 19. Lock-файлы: только `package-lock.json` v2/v3, отдельный лимит, распознавание чужих форматов
**Контекст:** реальные lock-файлы часто весят 1–5 MB, а пользователь может вставить lock-файл вместо `package.json`.
**Решение:** `parseLockfile` читает только `package-lock.json` v2/v3 с лимитом 10 MB (у `package.json` 1 MB). Битый, слишком большой или v1 lock-файл проверку не останавливает: вызывающий код продолжает по диапазонам (max satisfying) и показывает предупреждение. `detectLockfile` распознаёт lock-файл по содержимому без разбора: `# yarn lockfile v1` в тексте → yarn v1; первая значимая строка `__metadata:` → yarn berry, `lockfileVersion:` → pnpm (сначала пропускаются BOM, пустые строки, `#`-комментарии и маркер `---`); JSON с ключом `lockfileVersion` → npm. Распознавание идёт до проверки размера и JSON, поэтому для Paste и Upload сообщение будет «This is a lockfile…». Подсказка «add the lockfile in Upload» показывается только для npm.
**Почему:** проверка не должна падать из-за необязательного файла. «This is a lockfile» полезнее, чем «invalid JSON» или «too large». Признаки сверены с настоящими файлами (npm/cli, yarnpkg/berry, vuejs/core, vitejs/vite, этот репозиторий): lockfile v9 у pnpm 9+ начинается с `---`, а не с `lockfileVersion:`.
**Альтернативы:** общий лимит 1 MB (отсекает обычные lock-файлы); ошибка при битом lock-файле (лишний шаг для пользователя); разбор `pnpm-lock.yaml` / `yarn.lock` (нужен YAML-парсер, отложено).

### 20. Классификация спецификаторов (spec 7.4)
**Контекст:** нужно отличать версии из реестра от git, локальных путей и протоколов менеджеров пакетов.
**Решение:** `classifySpecifier` сначала разбирает `npm:<имя>@<спецификатор>` (без версии → `*`; вложенный алиас или не-реестровый спецификатор → invalid). Затем идёт список префиксов, которые не проверяются (`git+`, `git:`, `github:`, `gitlab:`, `bitbucket:`, `file:`, `link:`, `workspace:`, `portal:`, `patch:`, `catalog:`, `http(s):`, локальные пути) и шорткат `owner/repo`. Потом `semver.validRange`, потом правило имени тега.
**Почему:** порядок повторяет npm: диапазон важнее тега. `catalog:` у pnpm ведёт в реестр, но версию по одному `package.json` не узнать, поэтому такой пакет помечается «Not checked».
**Альтернативы:** `npm-package-arg` (новая зависимость ради одной функции).

### 21. Версии, отставание и статус пакета
**Контекст:** spec 3, 7.3 и screens 5.5 задают текущую и последнюю версию, отставание и статусы, но не говорят, что делать с пререлизами, 0.x и версиями, помеченными deprecated по отдельности.
**Решение:** `analyzePackage` (`src/server/analysis/analyze-package.ts`) и функции под ним:
- текущая версия берётся из lock-файла, даже если она не подходит под диапазон. Если записи в lock-файле нет или версия в ней не semver, берётся `semver.maxSatisfying` по диапазону, а тег разрешается через `dist-tags`;
- последняя версия — тег `latest`. Если он указывает на пререлиз или на версию, которой нет в `versions`, берётся максимальная стабильная версия. Если стабильных версий нет, пакет помечается «Not checked» с причиной `no-stable-version`;
- отставание считается по компонентам major/minor/patch строго по semver: 0.2 → 0.3 — minor. Пререлиз последней версии (1.0.0-rc → 1.0.0) — patch, текущая версия новее последней — up to date. `semver.diff` не используется: он считает 1.0.0-rc → 1.0.0 мажорным;
- deprecated — только если помечена последняя стабильная версия (spec 7.1). Deprecated важнее stale;
- последний релиз — самая поздняя публикация любой версии (включая пререлизы и бэкпорты) из `time`. Ключи `created`/`modified` и снятые с публикации версии не учитываются. Stale — если с последнего релиза прошло строго больше 12 календарных месяцев (UTC); текущее время передаётся параметром;
- причины «Not checked» возвращаются кодами (`not-from-registry`, `invalid-specifier`, `no-matching-version`, `unknown-tag`, `no-stable-version`), тексты будут в UI.
**Почему:** lock-файл — факт установки, диапазон — только предположение. Устаревшая старая версия значит «обновись», а это уже показывает отставание; пометка на последней версии значит, что автор бросил пакет. 0.x по semver совпадает с цифрами, которые видит пользователь. Пакет, который выпускает только пререлизы или бэкпорты, жив, поэтому он не stale.
**Альтернативы:** приоритет `latest`, если он подходит под диапазон (так делает npm при установке, но spec 3 говорит «максимальная подходящая»); 0.x по правилам caret (0.2 → 0.3 = major); deprecated и по установленной версии; дата релиза только версии `latest`.

### 22. Уязвимости: объединение записей OSV, «Fixed in» и критичность
**Контекст:** spec 7.1 и 7.3 требуют объединять записи OSV по `aliases`, брать высшую критичность и показывать «Fixed in» — наименьшую версию, исправленную по всем записям. Но spec не говорит, откуда брать версии-кандидаты, что делать с записями без метки критичности и как читать диапазоны `affected`.
**Решение:** `mergeVulnerabilities` (`src/server/analysis/merge-vulnerabilities.ts`):
- записи объединяются через union-find по `id` и `aliases`, транзитивно. Две записи связываются и через общий алиас, которого нет среди полученных записей (две GHSA с одним CVE). Записи с `withdrawn` пропускаются. В `ids` попадают ID записей и их алиасы, по порядку: GHSA, CVE, остальные, затем по алфавиту. Первый ID основной, его описание показывается;
- «Fixed in»: кандидаты — только события `fixed` из диапазонов `SEMVER`/`ECOSYSTEM` этого пакета (`affected` фильтруется по `npm` и имени), строго выше текущей версии. Ответ — наименьший кандидат, который не затронут ни одной записью (учитываются `introduced`, `fixed`, `last_affected` и список `versions`). Если такого нет — `null` («No fix available»);
- критичность записи (`src/server/analysis/severity.ts`): `MAL-*` → critical; метка GHSA `database_specific.severity` → её значение; иначе базовая оценка из вектора CVSS v3.0/3.1 (≥ 9 critical, ≥ 7 high, ≥ 4 moderate, иначе low); иначе moderate. Формула CVSS v3 написана своими силами по спецификации FIRST, CVSS v4 не считается.
**Почему:** версия из события `fixed` точно была выпущена как исправление, а для `last_affected` и списка `versions` следующую опубликованную версию без данных реестра не узнать. Метка GHSA есть почти у всех npm-записей. Вредоносный пакет (MAL) хуже любой уязвимости. Moderate для записи без данных учитывает её в оценке, но не делает её главной. Тексты и ссылки на источники будут в UI.
**Альтернативы:** минимальная из версий исправления (неверно, если другая запись ещё затрагивает эту версию — spec 7.3); кандидаты из списка версий реестра (точнее для `last_affected`, но нужен ещё один вход); low или «unknown» для записей без критичности (в spec только четыре уровня); библиотека для CVSS (новая зависимость ради одной формулы).

### 23. Оценка здоровья, счётчики, признаки breaking и команды обновления
**Контекст:** spec 7.1–7.3 и 7.5 задают веса, счётчики, признаки breaking и формат команд, но не говорят, что показывать без проверенных пакетов, как считать уязвимость на нескольких пакетах, какие тексты в release notes считать признаками и как обновлять алиас.
**Решение:**
- `healthScore` (`health-score.ts`): веса и потолки в константе `SCORE_RULES` — её же покажет поповер «How it's calculated». Мажорное отставание — 6 баллов за пакет, сколько бы мажоров ни было. Deprecated — по статусу пакета (а он ставится только по последней версии, решение 21). Непроверенные пакеты не участвуют, «Partial» — если их строго больше 20%. Если не проверено ничего, `score: null`, и UI показывает «—». `breakdown` по категориям даёт число, штраф после потолка и сам потолок;
- `reportCounts` (`report-counts.ts`): плитки отставания и «Vulnerable» считаются только по проверенным пакетам, разбивка — по высшей критичности пакета. «Dependencies (N)» — все пакеты, «Vulnerabilities (N)» — сумма объединённых уязвимостей по пакетам: одна GHSA на двух пакетах даёт 2, как пункты на вкладке и штраф в оценке;
- `isPossiblyBreaking` (`breaking-changes.ts`): мажорная версия — всегда; минорная — по признакам в release notes; патчи не проверяются. Признаки: заголовок markdown или строка целиком жирным со словами breaking / removed(removals) / deprecated(deprecations) / backwards incompatible; `BREAKING CHANGE` или `BREAKING:` заглавными в любом месте; conventional commit с `!` (`feat!:`, `fix(scope)!:`). Слово «deprecated» в обычном тексте не считается;
- `updateCommands` (`update-command.ts`): `npm i` / `pnpm add` / `yarn add`, dev-зависимости — отдельной командой с `-D`, пустая группа не выводится, дубли по имени убираются. Алиас пишется как `name@npm:real@version`.
**Почему:** 100 баллов для проекта, который не удалось проверить, вводят в заблуждение. spec 7.1 штрафует «пакет с мажорным отставанием», а не каждый мажор. Счёт по парам «пакет — уязвимость» совпадает с тем, что пользователь видит в списке. spec 7.2 говорит о «разделах», поэтому слово в обычном тексте не признак, иначе любой «fix deprecated warning» помечался бы как ломающий. Без `npm:` в команде установка переименовала бы зависимость.
**Альтернативы:** оценка 100 без проверенных пакетов; штраф за каждый мажор отставания; уникальные уязвимости по всему проекту для «Vulnerabilities (N)»; поиск ключевых слов по всему тексту release notes; проверка признаков и в патчах.

### 24. Модель данных и драйвер БД
**Контекст:** нужны гостевые отчёты на 7 дней, сохранённые проекты, повторные проверки с историей (задел 1.1), запись результата каждого пакета сразу по готовности, кэш внешних API и счётчики лимита. Плюс один драйвер для Neon dev-ветки, продового Neon и Postgres в CI.
**Решение:** схема в `src/server/db/schema.ts`, миграции drizzle-kit в `drizzle/`:
- `reports` — входные данные проверки (источник, `dependencies`, записи lock-файла, предупреждения, менеджер пакетов). Отчёт либо гостевой (`expires_at`), либо принадлежит проекту (`project_id`, один отчёт на проект): CHECK требует ровно одно из двух. «Save project» проставляет `project_id` и обнуляет `expires_at`, «Replace source» обновляет отчёт проекта. Id — случайный UUID, потому что гостевой отчёт открывается по ссылке;
- `projects` — имя и владелец. FK `owner_id` на таблицу пользователей Better Auth добавится в задаче 20 вместе с ней;
- `checks` — одна проверка отчёта со статусом `running / completed / partial / cancelled / failed`. Частичный уникальный индекс не даёт запустить вторую проверку, пока идёт первая. `score` и `vulnerability_count` — снимок при завершении для дашборда и истории; страница отчёта пересчитывает их чистыми функциями по `check_packages`;
- `check_packages` — PK `(check_id, name)`, снимок входа (`type`, `specifier`) и результат: версии, отставание, статус, причина «Not checked», уязвимости после `mergeVulnerabilities` в `jsonb`. Строка появляется, когда пакет обработан: Resume проверяет пакеты отчёта без строки, Retry failed — строки с причиной сбоя источника. Снимок входа сохраняет историю после замены источника;
- `api_cache` (ключ, `jsonb`, `expires_at`) и `rate_limits` (PK `(subject, window_start)`, фиксированное окно, decisions 44);
- удаление каскадное: проект → отчёт → проверки → результаты.

Драйвер — `postgres` (postgres.js) через `drizzle-orm/postgres-js`, клиент создаётся лениво в `getDb()` (`src/server/db/client.ts`) с `prepare: false`. SSL берётся из `sslmode=require` в URL Neon. `drizzle.config.ts` сам загружает `.env.local` через `process.loadEnvFile`, без `dotenv`.
**Почему:** входные данные живут в отчёте, а результаты — в проверках, поэтому «Check again» и Resume не требуют повторной загрузки файла, а история не теряется. Скалярные поля результата — колонки (по ним фильтрует история и дашборд), список уязвимостей — `jsonb`: он всегда читается целиком. postgres.js работает и с Neon, и с обычным Postgres (CI, Docker) и поддерживает интерактивные транзакции. `prepare: false` нужен для pooled URL Neon (PgBouncer в режиме transaction).
**Альтернативы:** `@neondatabase/serverless` (HTTP без интерактивных транзакций, не подключается к обычному Postgres без прокси); `pg` (то же, плюс `@types/pg`); отдельная таблица `project_sources` (лишний JOIN, у проекта один источник); результат пакета целиком в `jsonb` (нельзя фильтровать и сравнивать проверки в SQL).

### 25. Источники: кэш, ограничитель параллельности, повторы
**Контекст:** проверка делает сотни запросов к npm (позже OSV и GitHub). Нужны кэш на 1 час (decisions 4, spec 9), ограниченная параллельность и устойчивость к 429/5xx, при которой сбой одного пакета не валит отчёт.
**Решение:** `src/server/sources`:
- `withCache` поверх таблицы `api_cache`. В кэш пишется уже урезанный и провалидированный результат (`NpmPackageInfo`), а не сырой ответ. При чтении значение снова проверяется Zod-схемой, несовпадение считается промахом. Ошибки (404, лимит, 5xx) не кэшируются. Сбой самой БД кэша не роняет запрос: источник вызывается напрямую, ошибка пишется в лог;
- свой ограничитель `createLimiter(n)` без зависимостей. Освободившийся слот передаётся ожидающей задаче напрямую. Через ограничитель идут только сетевые запросы, попадания в кэш его не ждут;
- `fetchJson`: таймаут 10 с по умолчанию (у npm 30 с: полные документы `next` и `typescript` весят больше 2 MB в gzip, их загрузка заняла 12–23 с), до 2 повторов на 429, 5xx и сетевую ошибку. Таймаут не повторяется: медленный источник снова упрётся в него и потратит ещё 30 с. Повторы идут с экспоненциальной задержкой (500 мс, 1 с) с учётом `Retry-After`. Если ждать нужно дольше 5 с, повторов нет, сразу возвращается `rate-limited` с `retryAfterSeconds` (для «Try again in N minutes»). Ошибки — `Result` с кодами `not-found`, `rate-limited`, `unavailable`, `invalid-response`. Отмена через `AbortSignal` бросает исключение: это не сбой пакета, а остановка проверки;
- npm: полный документ пакета (у сокращённого `application/vnd.npm.install-v1+json` нет `time`, без него не посчитать stale). Описание, лицензия, homepage и repository сохраняются для карточки (задача 17).
**Почему:** полные документы популярных пакетов весят мегабайты, а нужны из них килобайты. Кэшировать ошибки — значит час показывать временный сбой. Ожидание дольше нескольких секунд на один пакет тормозит всю проверку и рискует лимитом длительности функции (decisions 16).
**Альтернативы:** `p-limit` (лишняя зависимость ради 20 строк); кэш сырых ответов (объём БД); кэш 404 с коротким TTL (экономия на опечатках не стоит сложности).

### 26. OSV и GitHub: кэш, частичные сбои, лимиты, менеджер пакетов
**Контекст:** проверке нужны уязвимости по точной версии каждого пакета (OSV), лендингу — package.json и lock-файл из публичного репозитория, карточке — release notes (GitHub). Нужно решить, что кэшировать, как вести себя при частичном сбое OSV, как распознать лимит GitHub и откуда брать менеджер пакетов (spec 7.5).
**Решение:**
- OSV (`src/server/sources/osv.ts`): `querybatch` отдаёт только ID, полные записи — `GET /v1/vulns/{id}`. Кэш двух уровней: `osv:query:<name>@<version>` (список ID) и `osv:vuln:<id>` (запись, урезанная до полей `OsvRecord`). Пакеты из кэша в batch не попадают; запись, общая для нескольких пакетов, загружается один раз. Упала пачка — ошибка у всех её пакетов; не загрузилась одна запись — ошибка только у пакетов, где она есть. `next_page_token` дозапрашивается только для вернувших его запросов, не больше 10 страниц. Пачка — до 1000 запросов: лимит в документации OSV не указан, при 300 зависимостях это только защита;
- GitHub (`src/server/sources/github.ts`): `GET /repos/{o}/{r}` → листинг корня `contents/` → raw-содержимое `package.json` и `package-lock.json` (`application/vnd.github.raw+json`: в JSON Contents API не отдаёт файлы больше 1 MB, а lock бывает до 10 MB). Исходники репозитория **не кэшируются**: это вход отчёта, он хранится в `reports` и перечитывается при «Check again» (decisions 42). Release notes кэшируются на 1 ч, берётся первая страница (100 релизов), черновики отбрасываются. `private: true` даёт тот же ответ, что и 404. Пустой репозиторий (404 листинга) = «No package.json». Lock-файл, который не загрузился, пропускается с записью в лог. Версия API `2026-03-10`; её breaking changes не затрагивают используемые эндпоинты. Токен клиент получает параметром, env читает вызывающий код;
- лимит GitHub (`fetchText`/`fetchJson` в `http.ts`): 403 или 429 с `x-ratelimit-remaining: 0` → `rate-limited` до `x-ratelimit-reset`; `retry-after` → его значение; 403 с сообщением о rate limit без заголовков → 60 с (так советует документация GitHub для secondary limit). Обычный 403 остаётся `unavailable`. Ожидание больше 5 с не повторяется (decisions 25), а уходит в текст «Try again in N minutes», N округляется вверх и не меньше 1;
- `detectPackageManager` (`src/server/analysis/detect-package-manager.ts`): поле `packageManager` (`pnpm@…`, `yarn@…`, `npm@…`) → `pnpm-lock.yaml` → `yarn.lock` → npm. Неизвестный менеджер в поле (`bun@…`) уходит дальше по цепочке. При обоих lock-файлах выигрывает pnpm, по порядку spec;
- `parseGithubRepoUrl` принимает только корень репозитория (`/tree/…` — ошибка, проверяется только корневой package.json). `parseRepositoryField` разбирает поле `repository` из npm для release notes и игнорирует путь до подпапки.
**Почему:** неполный список уязвимостей показал бы пакет безопаснее, чем он есть, поэтому лучше «Not checked». Кэш исходников репозитория час показывал бы старый package.json после исправления. Приватные данные spec 9 запрещает читать, а токен автора их видит.
**Альтернативы:** кэш исходников на 1 ч (противоречит ожиданию пользователя после пуша); Contents API в JSON с base64 (лимит 1 MB); показ частичного списка уязвимостей; все страницы releases (лишние запросы ради старых версий, которые карточка всё равно сворачивает).

### 27. Движок проверки: аренда, наблюдатель, пачки OSV, статусы
**Контекст:** проверка идёт внутри SSE route handler (decisions 16), каждый результат сразу пишется в `check_packages`. Один и тот же `checks` может открыть несколько потоков: две вкладки, автопереподключение EventSource, новое открытие после таймаута Vercel, когда статус остался `running`. Нужно, чтобы пакеты проверял ровно один поток, остальные видели прогресс, а проверка, чей поток умер, доделывалась без ручного Resume.
**Решение:**
- **Аренда** — колонка `checks.lease_until`. Поток захватывает её условным `UPDATE … WHERE status = 'running' AND (lease_until IS NULL OR lease_until < now)` на 30 с и продлевает таймером каждые 10 с (не по готовности пакета: один документ npm грузится до 30 с). Продление вернуло `false` (проверку отменили через `cancelCheck`) — поток останавливается. Строки пишутся с `ON CONFLICT DO NOTHING`: если аренда всё же истекла и пакет записал другой поток, остаётся первая строка и второго события нет;
- **наблюдатель** — поток без аренды раз в секунду читает статус, потом строки (строки пишутся до смены статуса, значит после завершения они полные) и шлёт те же события. При каждом опросе пытается взять аренду: получилось — проверку доделывает он;
- **события SSE**: `progress {checked, total}`, `package {строка}`, `done {status, failureReason, retryAt}`, `error {}`; `: ping` каждые 15 с. Строки, уже записанные до подключения, не пересылаются: их отдаёт страница, по `done` клиент обновляет данные;
- **отмена**: закрытие EventSource → статус `cancelled`, строки сохраняются. Next.js прерывает `request.signal`, когда ответ закрывается раньше конца (`createAbortController` в `next-request.ts`, e2e-тест `cancel-request`); `cancel()` у `ReadableStream` слушается тоже. `AbortSignal` уходит в источники, ожидание `Promise.allSettled`, чтобы ни одна строка не легла после `done`;
- **мягкий дедлайн 280 с** (раньше `maxDuration = 300`) — не отмена: аренда освобождается, поток закрывается без `done`, EventSource сам переподключается, и новый вызов функции доделывает пакеты без строки. Пользователь не видит «Check cancelled», которого не делал. Если за вызов не записано ни одного пакета, проверка всё же завершается `cancelled`, иначе переподключения жгли бы вызовы функции бесконечно. Наблюдатель по дедлайну тоже просто закрывает поток. Клиентский хук (задача 12) должен считать конец потока без `done` переподключением, а не ошибкой;
- **пачки OSV**: проанализированные пакеты копятся в пачку `querybatch`, она уходит при 25 пакетах, когда не осталось незавершённых запросов npm или через 300 мс после первого пакета пачки: иначе один медленный документ npm держал бы уязвимости всех остальных;
- **статус** (`checkOutcome`, чистая функция): `partial` — у части пакетов сбой источника (`registry-rate-limited`, `registry-unavailable`, `vulnerabilities-unavailable`); `failed` — сбой у всех пакетов, которые искались в реестре, с кодом причины (лимит важнее, у него есть время повтора). Git/file-зависимости и пакет, которого нет в npm (`not-in-registry`), проверку частичной не делают: Retry их не исправит. Непредвиденная ошибка (БД) → `failed` с `internal-error` по возможности, иначе событие `error` и аренда истекает сама;
- **причина провала — код, а не текст** (`failure_reason`), время повтора — `checks.retry_at`: страница считает «Try again in N minutes» от текущего момента, текст лежит в копирайте фичи. Без `Retry-After` берётся 60 с;
- **Resume** возвращает `cancelled`/`partial`/`failed` в `running`, проверяются пакеты без строки. **Retry failed** и «Try again» сначала удаляют строки со сбоем источника. Обе операции — `reopenCheck` в транзакции с `SELECT … FOR UPDATE`; вторая running-проверка отчёта упирается в частичный уникальный индекс → `already-running`;
- оркестратор получает store, кэш, ограничитель и часы параметрами (`CheckStore` — интерфейс, Postgres-реализация в `src/server/db/check-store.ts`), поэтому unit-тесты идут на in-memory store и MSW без БД.
**Почему:** аренда в той же таблице не требует ни advisory locks (не работают через PgBouncer в режиме transaction), ни отдельного сервиса. Наблюдатель через опрос БД проще, чем рассылка событий между функциями, и на Vercel без общего состояния между инстансами другого пути нет. Коды вместо текста оставляют перевод в UI.
**Альтернативы:** дедлайн как отмена (пользователь видит «Check cancelled» и жмёт Resume сам); без защиты (два потока делают одну работу, зависший `running` снимается только вручную); аренда без наблюдателя (вторая вкладка не видит прогресс); OSV-запрос на каждый пакет (в 25 раз больше запросов); одна пачка OSV в конце (результаты появляются только после всех запросов npm).

### 28. Лендинг: создание гостевого отчёта, lock-файл из Upload сжимается в браузере
**Контекст:** «Check dependencies» создаёт гостевой отчёт через Server Action (screens 5.1). У Server Action лимит тела по умолчанию 1 MB, у функции Vercel — 4.5 MB, и поднять его нельзя. `package.json` весит до 1 MB, а `package-lock.json` — до 10 MB (решение 19). Кроме того, после редиректа предупреждение о битом lock-файле должно где-то храниться, чтобы отчёт его показал.
**Решение:**
- браузер при выборе файла сжимает lock-файл в gzip (`CompressionStream`, `gzipText` в `src/features/landing/upload-files.ts`) и отправляет его полем FormData. Форма отправляется вручную через `startTransition(() => formAction(formData))`, потому что `Blob` из состояния нельзя положить в поле формы. Файлы различаются по содержимому (`detectLockfile`), а не по имени; файл больше 10 MB браузер отклоняет до отправки;
- сервер (`readUploadedLockfile`, `src/server/lockfile-upload.ts`) распаковывает его с `maxOutputLength` = 10 MB и разбирает тем же `parseLockfile`. Переполнение при распаковке → предупреждение `lockfile-too-large`, не gzip или v1 → `lockfile-unsupported`, проверка идёт по диапазонам;
- `serverActions.bodySizeLimit` = `4mb`: `package.json` до 1 MB плюс сжатый lock-файл (10 MB сжимаются примерно до 1 MB), ниже лимита Vercel;
- `buildReportInput` (`src/server/analysis/report-input.ts`, чистая функция) собирает вход отчёта для всех трёх источников: `parseManifest` → записи lock-файла только для прямых зависимостей → `detectPackageManager`. Предупреждения lock-файла хранятся в `reports.warnings` вместе с `workspaces` (тип `ReportWarning`, `jsonb`, без миграции), показывает их отчёт (задача 12);
- `createGuestReport` (`src/server/db/reports.ts`) создаёт отчёт (`expires_at` = +7 дней) и первую проверку в одной транзакции, затем `redirect` на `/r/[id]/dependencies`;
- форма на `useActionState` без React Hook Form: одно поле, вся валидация на сервере теми же кодами ошибок, RHF появится в задаче 23. В состоянии формы есть счётчик `attempt`: одинаковая ошибка дважды снова ставит фокус на поле, а правка поля скрывает ошибку, относящуюся к нему.
**Почему:** сервер остаётся единственным местом, где lock-файл разбирается и проверяется, а сжатие укладывает 10 MB в лимит без внешнего хранилища и новых зависимостей. Лимит распаковки защищает от архива, который раскрывается в гигабайты. Отчёт без проверки, оставшийся после сбоя второй записи, открывался бы пустым, поэтому нужна одна транзакция.
**Альтернативы:** разбор lock-файла в браузере с отправкой только прямых зависимостей (сервер не видит исходный файл); загрузка во внешнее хранилище (Vercel Blob/S3 — лишний сервис ради одного файла); лимит lock-файла около 4 MB (крупные проекты теряют точные версии); `store.createCheck` отдельным запросом после вставки отчёта.

### 29. Страница отчёта: данные с сервера, поток только дополняет
**Контекст:** отчёт (screens 5.4) показывает одну и ту же страницу в состояниях «первая проверка», «повторная проверка», «частично», «отменено», «провал», «истёк», 404. Строки приходят из двух мест: из БД (уже записанные пакеты) и из SSE (decisions 27). Нужно, чтобы эти источники не расходились и чтобы итоговая сводка считалась в одном месте.
**Решение:**
- layout `/r/[id]/(report)` до стриминга проверяет id (Zod `uuid`), существование отчёта (`getReportMeta`) и истечение (`isReportExpired` при каждом открытии, decisions 11), поэтому 404 отдаётся с настоящим статусом. Остальное грузится под `Suspense` со скелетоном (`ReportSkeleton`);
- `ReportView` (Server Component) читает отчёт, последнюю проверку и, если она `running`, предыдущую (`pickChecks`): во время «Check again» сводка и строки берутся из предыдущей проверки, пока не придёт `done`. Сводка (`summarizeRows`) считается только на сервере;
- клиент (`ReportProvider` + `useCheckStream`) лишь накладывает строки из потока поверх строк страницы (`buildRows`: предыдущая проверка → текущая → поток), по `done` вызывает `router.refresh()`. Провайдер перемонтируется по ключу `checkId:status`, так что поток всегда стартует от только что загруженных данных;
- Server Actions (`checkAgain`, `cancel`, `resume`, `retry`) не возвращают ошибок, а заканчиваются `refresh()`: «уже идёт», «не идёт» или «истёк» видны по состоянию из БД;
- таблица на TanStack Table v9 (`useTable` + `tableFeatures`), признаки и колонки объявлены на уровне модуля, чтобы модель строк не пересобиралась на каждый рендер. В задаче 12 — только колонка Package со скелетоном и подсветкой обновлённой строки, остальное — задача 13;
- `MOCK_EXTERNAL=1` подключает MSW в `src/instrumentation.ts` (только Node-рантайм): фейковые npm и OSV из `src/server/sources/mock/handlers.ts` с задержкой, пакеты `fail-*` получают 503 — так все состояния страницы воспроизводятся локально и в e2e без сети;
- `notFound()` до стриминга (настоящий 404) в Next 16 отдаёт аварийную оболочку `<html id="__next_error__">`, а корневой layout дорисовывается на клиенте, где inline-скрипт темы в `<head>` не выполняется. `ThemeScriptFallback` в корневом layout проверяет `color-scheme` на `<html>` (скрипт его ставит всегда) и, если пусто, вставляет тот же `themeScript` элементом `<script>`. Перенос `notFound()` из layout в page не помогает: оболочка та же.
**Почему:** один источник правды для сводки и статуса (БД через сервер) убирает расхождения между вкладками и после переподключения; клиенту не нужно повторять логику оценки. Обновление через `refresh()` проще, чем отдельный протокол ошибок для каждого действия.
**Альтернативы:** вся страница на клиенте с загрузкой через route handler (дублирует логику сводки, теряется статус 404); пересчёт сводки на клиенте по событиям потока (две реализации подсчёта); ответы Server Actions с кодами ошибок и тостами (больше состояний, а итог всё равно читается из БД).

### 30. Фильтры таблицы в URL: формат параметров и поведение
**Контекст:** spec 6 и screens 5.4–5.5 требуют, чтобы поиск, фильтры и сортировка жили в адресе (ссылка открывает ту же выборку), сохранялись при смене вкладки и включались кликом по плитке сводки (decisions 6).
**Решение:**
- nuqs 2 (`NuqsAdapter` в корневом layout); парсеры, сериализатор и чистая `filterRows` — в `src/features/report/filters.ts`, их же используют плитки и «Show» в плашке частичной проверки;
- параметры: `q`, `type` (`prod|dev`), `lag` (`current|patch|minor|major`, «N majors» входит в `major`), `vuln` (`yes|no`), `status` (`active|stale|deprecated|unchecked`), `sort` (`name|behind|vulns|released`, `-` в начале — по убыванию). Значения по умолчанию в адрес не пишутся, неизвестные значения читаются как «нет фильтра»;
- каждый фильтр — одиночный выбор (radio-меню и один чип на фильтр);
- поиск: адрес обновляется с `debounce(200)`, а строки фильтруются по отдельному значению с той же задержкой, потому что локальное состояние nuqs меняется сразу; очистка поля применяется мгновенно;
- строки в ожидании результата проходят только поиск по имени, любой другой фильтр их скрывает;
- плитка добавляет свой фильтр к текущему адресу (остальные фильтры сохраняются), на активной плитке ссылка снимает фильтр;
- «Clear all» / «Clear filters» сбрасывают поиск и фильтры, сортировку оставляют;
- «All N packages are up to date.» — только без фильтров, после проверки, когда все пакеты проверены, актуальны и без уязвимостей.
**Почему:** короткие читаемые ключи делают ссылку понятной; одиночный выбор покрывает сценарии screens 5.5 и плиток без мультивыбора в чипах; один сериализатор для всех ссылок гарантирует одинаковый формат. Без проверки уязвимостей «всё актуально» прятало бы уязвимый пакет без фикса.
**Альтернативы:** мультивыбор через `parseAsArrayOf` (больше чипов и сложнее плитки); `sort` + отдельный `dir` (длиннее ссылка); плитка заменяет все фильтры (теряется поиск пользователя); фильтрация сразу по вводу (противоречит задержке 200 мс из screens 5.5).

### 31. Выделение, виртуализация и мобильная таблица
**Контекст:** screens 5.5 и spec 6.4, 7.5: массовое выделение с «Copy update command», отзывчивая таблица при 500+ пакетах с липким заголовком, на < 768px — карточки и шторка «Filters». Переключатель npm / pnpm / yarn — задача 18.
**Решение:**
- выделение — локальное состояние таблицы (не URL); строки, скрытые фильтром или поиском, снимаются с выделения, поэтому «N selected» и команда всегда совпадают с экраном; чекбокс в заголовке выделяет все отфильтрованные строки; новая проверка сбрасывает выделение;
- команда собирается менеджером пакетов отчёта (`reports.packageManager`, задача 9) через `updateCommands`; prod- и dev-команды склеиваются через ` && `, чтобы одна вставка выполнила обе; в команду идут только проверенные пакеты с отставанием; если таких нет — тост «Selected packages are already up to date.»;
- виртуализация (`@tanstack/react-virtual`) включается от 500 показанных строк: таблица прокручивается в собственном блоке `max-h-160`, заголовок `sticky` внутри него, строки-отступы сверху и снизу сохраняют настоящий `<table>`, `table-fixed` + `<colgroup>` не дают колонкам прыгать; карточки прокручиваются вместе со страницей (`useWindowVirtualizer`);
- таблица и карточки рендерятся обе, лишнюю прячет CSS (`hidden md:block` / `md:hidden`); фильтры на мобильных — нижняя шторка на Radix Dialog с radio-группами;
- панель инструментов (и панель выделения на её месте) прилипает к верху страницы.
**Почему:** выделение только видимых строк исключает копирование команды для пакетов, которых пользователь не видит; собственный блок прокрутки нужен, потому что `overflow-x-auto` контейнера таблицы ломает `sticky` относительно окна; переключение через CSS не даёт мигания таблицы на мобильных при гидрации.
**Альтернативы:** сохранять выделение скрытых строк (команда включает невидимые пакеты); команды построчно (вставка в терминал менее предсказуема); выбор таблица/карточки через `matchMedia` (мигание после гидрации, на сервере ширина неизвестна); window-виртуализация таблицы с `overflow: clip` (обрезает колонки на ширинах 768–1024px).

### 32. Вкладка Vulnerabilities: источник ссылок, фильтры и пустые состояния
**Контекст:** screens 5.6: список уязвимостей по критичности, идентификатор — ссылка на источник в новой вкладке, «Details» → карточка пакета (задача 17), пустое состояние «No known vulnerabilities in your dependencies.» Источник ссылки, действие фильтров таблицы и поведение при незавершённой проверке в документах не заданы.
**Решение:**
- список строится на клиенте из тех же строк отчёта (`useReport().rows`), что и таблица, поэтому растёт по SSE во время проверки; группировка — чистая `groupVulnerabilities` в `src/features/report/vulnerability-groups.ts`. Одна уязвимость в двух пакетах — два элемента (так же её считает «Vulnerabilities (N)», spec 7.3); внутри группы — по имени пакета, затем по ID;
- ссылка для любого ID — `https://osv.dev/vulnerability/<id>`;
- фильтры таблицы (`q`, `type`, `lag`, `vuln`, `status`, `sort`) к вкладке не применяются, но остаются в адресе и возвращаются при переходе на Dependencies;
- «Details» пишет `?pkg=<имя>` (остальные параметры сохраняются); отдельного параметра вкладки карточки нет — карточка открывает первую непустую вкладку, у уязвимого пакета это Vulnerabilities (screens 5.9);
- пока идёт проверка и уязвимостей не найдено — скелетон; если проверка не идёт и не проверен ни один пакет (отмена или сбой до первого результата) — «No packages have been checked yet.»; «No known vulnerabilities…» — только когда проверен хотя бы один пакет.
**Почему:** OSV — источник данных, его страница принимает GHSA, CVE и другие алиасы, так что одна функция покрывает все ID. Число во вкладке считается без фильтров, и список должен с ним совпадать. «Нет уязвимостей» при нуле проверенных пакетов — ложное утверждение о безопасности; плашка частичной проверки над вкладками объясняет причину.
**Альтернативы:** ссылка по префиксу (GHSA → github.com/advisories, CVE → nvd.nist.gov; два формата и неизвестные префиксы без ссылки); применять фильтры таблицы к списку (расходится с числом во вкладке, нет панели, чтобы их увидеть и снять); одна запись на уязвимость со списком пакетов (расходится со счётчиком spec 7.3); пустое состояние при нуле проверенных (вводит в заблуждение).

### 33. Карточка пакета: загрузка деталей, история, порядок `j`/`k`, фокус
**Контекст:** screens 5.9: панель поверх отчёта по `?pkg=` на обеих вкладках, `j`/`k` «в текущем порядке таблицы», Esc возвращает фокус на строку, пакет не из отчёта — тост. Описание, лицензия, ссылки и даты релизов в `check_packages` не хранятся, они есть только в документе npm (кэш `api_cache`, decisions 25). Способ загрузки, поведение истории и порядок на вкладке без таблицы в документах не заданы.
**Решение:**
- то, что есть в строке отчёта (версии, отставание, статус, объединённые уязвимости), показывается сразу; описание, лицензия, ссылки npm/Repository и шкала релизов — через Server Action `getPackageDetails(reportId, name)` (`src/features/report/package-actions.ts`). Сервер сам берёт последнюю строку пакета из проверок отчёта (`getReportPackage`), проверяет uuid, истечение и что пакет проверен, и только тогда зовёт `fetchNpmPackage` с тем же кэшем, что и проверка. Ответ собирает чистая `toPackageDetails`. Сбой — «Couldn't load package details. Retry» в этом блоке, остальная панель работает;
- шкала (`releaseTimeline`): стабильные версии в `(current, latest]`, позиция по дате (если у какой-то версии нет даты — равномерно), смена мажора = «возможно ломающая» (spec 7.2). Минорные с признаками из release notes добавит задача 19;
- в задаче 17 уязвимости — секция «Vulnerabilities (N)» без вкладок: одна запись на уязвимость, все ID ссылками на OSV, полное `details` текстом. Вкладки появятся в задаче 19 вместе с Release notes;
- история: открытие и закрытие пишут `pkg` с `push` («назад» закрывает панель), `j`/`k` — `replace`, неизвестный `pkg` убирается `replace` с тостом «Package not found in this project»;
- `j`/`k` идут по `orderedRows` (`defaultOrder` → `filterRows` → `sortRows` по параметрам адреса), а не по отрисованной таблице: на вкладке Vulnerabilities таблицы нет. RTL-тест сверяет порядок таблицы с `orderedRows` для каждого `sort`. Без зацикливания; пакет, скрытый фильтром, — `j` начинает с первой строки; клавиши игнорируются в полях ввода и с модификаторами;
- возврат фокуса: `onCloseAutoFocus` ищет видимый `[data-package=<имя>]` (строка таблицы, карточка на мобильных или «Details»); если его нет (отфильтрован, не отрисован виртуализацией), фокус возвращает Radix;
- панель — `SheetContent side="end"`: справа 480px на ≥ 768px, на мобильных на весь экран снизу.
**Почему:** route handlers по CLAUDE.md только для SSE, cron и webhooks; `shallow: false` для `pkg` перерисовывал бы весь `ReportView` с чтением БД на каждый `j`/`k`. Server Actions Next выполняет по очереди, но у панели один запрос за раз. Версии с сервера, а не от клиента, не дают через action загружать произвольные пакеты. `push` на открытие делает «назад» предсказуемым (screens 2), `replace` на `j`/`k` не засоряет историю.
**Альтернативы:** GET route handler (против конвенции проекта); загрузка деталей в Server Component через `searchParams` (полная перерисовка отчёта на каждое переключение); хранить описание и лицензию в `check_packages` (миграция и данные, нужные только карточке, а шкале всё равно нужен `time`); `j`/`k` по порядку списка уязвимостей на второй вкладке (расходится с «порядком таблицы» из screens 5.9); вкладки с пустой Release notes уже сейчас.

### 34. E2E с базой и моками в CI
**Контекст:** в карточке пакета появлялся горизонтальный скролл. Длинный URL без пробелов и дефисов в тексте OSV задавал min-content grid-колонки, а `break-words` (`overflow-wrap: break-word`) её не уменьшает. Баг виден только при настоящей вёрстке: jsdom её не считает, а e2e в CI работали без базы, поэтому страницы отчёта там не открывались.
**Решение:**
- тексты из внешних источников в карточке (описание пакета, summary и details уязвимости) переносятся через `wrap-anywhere` (`overflow-wrap: anywhere`): визуально перенос тот же, но min-content становится нулевым и колонка не растягивается;
- job `e2e` поднимает service-контейнер `postgres:17` (версия по умолчанию у Neon), применяет `pnpm db:migrate` и запускает приложение с `MOCK_EXTERNAL=1` и `MOCK_EXTERNAL_DELAY_MS=200`. Логин и пароль контейнера одноразовые и лежат в workflow открыто, это не секрет;
- в моках OSV у axios в details ссылка на коммит с 40-символьным хешем: без пробелов и дефисов браузеру негде её перенести. `tests/e2e/package-card.spec.ts` открывает карточку на 1440 и 390px и проверяет, что ни один прокручиваемый элемент в ней не шире своей области. Без исправления тест падает на обеих ширинах;
- локально e2e с моками нужно гонять на чистой базе, например `docker run --rm -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=radar -p 55432:5432 postgres:17` и `DATABASE_URL=postgres://postgres:postgres@localhost:55432/radar`. С базой из `.env.local` `api_cache` может отдать настоящие ответы npm и OSV раньше моков (TTL 1 ч).
**Почему:** база в CI нужна и остальным e2e по spec 12 (задача 29), а пустая база гарантирует, что приложение видит только моки. Проверка «ничто не прокручивается вбок» не зависит от классов и ловит любой будущий источник переполнения в карточке.
**Альтернативы:** `grid-cols-1` / `min-w-0` на каждом уровне grid в карточке (лечит симптом в одном месте, следующий вложенный grid сломается снова); `overflow-x-hidden` на панели (прячет текст, а не переносит); unit-тест в jsdom (там нет вёрстки); Neon-ветка для CI (внешний сервис, секрет в репозитории и общее состояние между запусками).

### 35. Подсказка про `j`/`k`/Esc в карточке пакета
**Контекст:** `j`/`k` и Esc в карточке работают (screens 5.9, 6), но в интерфейсе о них ничего не сказано, догадаться самому нельзя. В screens.md подсказка не описана.
**Решение:** в нижней панели карточки на ≥ 768px отдельной строкой выводится «`j` `k` next / previous · `Esc` close» приглушённым текстом, клавиши оформлены `<kbd>` как `/` в поиске. Нижняя панель теперь есть всегда; если в ней только подсказка, на мобильных панель скрыта.
**Почему:** подсказка видна именно там, где клавиши работают, и её видят гости. Одна строка мелким шрифтом не перегружает панель. На телефоне нет физической клавиатуры.
**Альтернативы:** тултип (у `j`/`k` нет элемента, к которому его привязать); памятка в настройках (гостям `/settings` недоступен, туда почти никто не заходит); кнопки ↑↓ в шапке с тултипом (новые элементы, которых нет в screens 5.9); диалог по `?` (о нём тоже никто не узнает).

### 36. Переключатель менеджера пакетов: хранение выбора
**Контекст:** spec 7.5: рядом с каждой кнопкой «Copy update command» — переключатель npm / pnpm / yarn, по умолчанию менеджер отчёта (`reports.packageManager`, задача 9), выбор «запоминается в браузере». Для чего именно запоминается — для отчёта или для браузера целиком — в spec не сказано.
**Решение:**
- выбор хранится в `localStorage` по ключу `package-manager:<reportId>`, отдельно для каждого отчёта; без записи — менеджер, определённый по репозиторию;
- хук `usePackageManager` (`src/features/report/package-manager-preference.ts`) на `useSyncExternalStore`: на сервере и при гидрации — определённый менеджер, после гидрации — сохранённый; неизвестное значение в хранилище игнорируется; панель выделения и карточка подписаны на одно хранилище и переключаются вместе, событие `storage` подхватывает выбор из другой вкладки;
- если хранилище недоступно (заблокированы данные сайта), выбор живёт в памяти до перезагрузки;
- переключатель — `SegmentedControl` (`src/components/ui`) на Radix `ToggleGroup type="single"`: это `radiogroup` с навигацией стрелками; повторный клик по активному варианту выбор не снимает;
- менеджер выбирается в `ReportProvider`, поэтому `useReport().packageManager` у всех потребителей уже учитывает выбор.
**Почему:** определение по репозиторию полезно, и глобальный выбор ломал бы его: выбранный однажды pnpm подставлялся бы в yarn-проект. Сервер не видит `localStorage`, поэтому начальное значение должно совпадать с серверным, иначе будет ошибка гидрации.
**Альтернативы:** один ключ на браузер (перекрывает определение во всех отчётах); хранение на сервере (у гостя нет аккаунта, для проектов можно добавить позже); Tabs или DropdownMenu (вкладки — это переход к содержимому, а меню прячет текущий выбор за лишним кликом).

### 37. Release notes в карточке пакета
**Контекст:** screens 5.9: вкладка «Release notes» с версиями от новых к старым, пометка «Possibly breaking», пустое состояние и «Couldn't load release notes. Retry», при котором остальная панель работает. Минорные версии с признаками из release notes должны краснеть на шкале (decisions 33). Тело релиза на GitHub — markdown, в стеке не было библиотеки для него.
**Решение:**
- отдельный Server Action `getReleaseNotes` рядом с `getPackageDetails`, общая проверка входа (`loadCheckedPackage`). Оба запускаются при открытии карточки, у каждого свои загрузка, ошибка и Retry (`useCheckedLoad`). Флаги нужны шкале, поэтому notes грузятся сразу, а не по клику на вкладку;
- репозиторий берётся из поля `repository` в npm (`parseRepositoryField`), не GitHub или нет поля → пустое состояние, ссылка «Open repository», если есть адрес. 404 репозитория — тоже «нет release notes», а не ошибка; лимит, 5xx и неверный ответ → ошибка с Retry;
- версия из тега (`releaseVersion`): `1.2.3`, `v1.2.3`, `name@1.2.3`, `@scope/name@1.2.3`, `name-v1.2.3`. Теги других пакетов монорепо и prerelease пропускаются. Показываются только стабильные версии из `(current, latest]`, у которых есть релиз; при двух релизах одной версии берётся более новый;
- `possiblyBreaking` считается `isPossiblyBreaking` относительно предыдущей версии в npm, а не предыдущего релиза: без релиза у 2.0.0 версия 2.1.0 иначе выглядела бы мажором от 1.x;
- шкала (`ReleaseTimeline`) получает набор помеченных версий от карточки: `releaseTimeline` на сервере не меняется, потому что notes приходят другим запросом. Красная точка — мажор или помеченный минор, крупная — только мажор;
- вкладка по умолчанию: Vulnerabilities, если N > 0, иначе Release notes (известно сразу, notes ждать не нужно). Версии свёрнуты через нативный `<details>`;
- markdown — `react-markdown` + `remark-gfm` без `rehype-raw`: `skipHtml` убирает сырой HTML, `img` запрещены (`disallowedElements`, `unwrapDisallowed`), ссылки открываются в новой вкладке, заголовки автора сдвигаются на h4–h6 под заголовки карточки, `pre` переносится, а не прокручивается (decisions 34). Подсказка «Detected automatically from release notes» есть и в тултипе бейджа, и текстом внутри раскрытой версии: тултип срабатывает только на hover.
**Почему:** раздельные действия дают раздельные сбои, как требует screens 5.9. Тело релиза — чужой текст, поэтому HTML и внешние картинки (трекеры) не попадают в страницу. Без разметки списки и заголовки release notes читаются как сырой текст с `##` и `-`.
**Альтернативы:** notes внутри `getPackageDetails` (один сбой GitHub прячет описание и шкалу); загрузка по клику на вкладку (шкала без флагов минора); простой текст с `whitespace-pre-line` (без зависимости, но нечитаемо); свой мини-рендер markdown (больше кода и тестов); показывать версии без релиза заглушкой (длинный список пустых пунктов у пакетов, которые не публикуют релизы для каждой версии).

### 38. `k` — следующий пакет, `j` — предыдущий
**Контекст:** в screens 5.9 и 6 было «`j` / `k` — следующий / предыдущий», как в vim, Gmail и GitHub. Автор решил наоборот.
**Решение:** `k` открывает следующий пакет в порядке таблицы, `j` — предыдущий; пакет, скрытый фильтром, — `k` начинает с первой строки (вместо `j` из decisions 33). Подсказка в карточке (decisions 35) — «`k` `j` next / previous · `Esc` close». screens.md обновлён.
**Почему:** решение автора продукта.
**Альтернативы:** оставить раскладку vim (`j` вниз, `k` вверх), привычную пользователям GitHub и Gmail.

### 39. «Copy update command» для показанных пакетов в тулбаре
**Контекст:** скопировать команду для всех зависимостей можно было только через чекбокс в заголовке таблицы и панель выделения — до этого не догадаться. В screens 5.5 такой кнопки нет.
**Решение:** в тулбаре рядом со «Showing N of M» — кнопка «Copy update command (N)» и переключатель npm / pnpm / yarn. Команда строится тем же `selectionCommand` из строк после фильтров и поиска: без фильтров это все зависимости, с фильтром — только показанные. N — число проверенных пакетов с отставанием (`updateTargets`). Кнопки нет, если обновлять нечего; пока строки выделены, тулбар как и раньше заменяет панель выделения. Мажорные обновления не исключаются: ограничить их можно фильтром «Behind».
**Почему:** команда совпадает с тем, что на экране, как у выделения (decisions 31). Один код сборки команды для выделения, тулбара и карточки.
**Альтернативы:** кнопка всегда для всех зависимостей отчёта (расходится с выделением и фильтрами); только мажорные/только безопасные обновления (лишний выбор, фильтр уже это даёт); пункт в меню «⋯» отчёта (снова прячет действие).

### 40. Предупреждение о мажорных обновлениях при копировании команды
**Контекст:** команда из тулбара и панели выделения может молча поднять пакеты через мажор, а пользователь вставит её, не открыв карточки и release notes.
**Решение:** копирование не блокируется; если в команде есть мажорные обновления (`lagKind === "major"` среди `updateTargets`), тост после копирования — заголовок «Update command copied» и под ним отдельной строкой «Includes N major updates: a, b and K more. Check release notes before applying.». Команды в тосте успеха больше нет (она уже в буфере и только раздувала тост); тост ошибки её оставляет, чтобы скопировать вручную. Имена — `row.name` в порядке таблицы по умолчанию (не выбранная колонка и не порядок команды, где dev идут после prod), не больше двух. Только тулбар и панель выделения: в карточке один пакет, и его отставание видно рядом с кнопкой. При ошибке копирования — прежний «Couldn't copy the command.» без предупреждения. Длительность тоста прежняя (5 с, действия нет).
**Почему:** мажорное обновление — это обычный осознанный шаг, блокировка или подтверждение мешали бы чаще, чем помогали; тост сообщает о риске в момент действия и не требует лишних кликов.
**Альтернативы:** диалог подтверждения перед копированием (лишний клик на каждое копирование); исключать мажорные из команды (расходится с выделением и счётчиком N, фильтр «Behind» уже это даёт); перечислять все имена (тост разрастается при десятках пакетов).

### 41. Авторизация: Better Auth, защита маршрутов, `next`, письма
**Контекст:** задача 20: GitHub OAuth и magic link (15 мин), `/login?next=`, `/login/check-email`, просроченная ссылка, защищённые маршруты, шапка приложения (screens 2, 4.2, 5.2, 5.3).
**Решение:**
- Better Auth 1.7 с `drizzleAdapter` (`better-auth/adapters/drizzle`), таблицы `user`, `session`, `account`, `verification` описаны в `schema.ts` руками по схеме CLI (колонки snake_case, `timestamptz`, как остальная схема); `projects.owner_id` → `user.id` с `on delete cascade`. Инстанс ленивый (`getAuth()`), как `getDb()`; `getSession()` сначала вызывает `headers()`, поэтому сборка не создаёт Better Auth и не требует его env. GitHub подключается, только если заданы `GITHUB_CLIENT_ID/SECRET`. `baseURL` — из `BETTER_AUTH_URL`, вне production по умолчанию `http://localhost:3000`: Server Action вызывает Better Auth без URL запроса, и без `baseURL` ссылку в письме не собрать.
- Защита в два слоя: `src/proxy.ts` (Next 16) для `/projects/*` и `/settings/*` проверяет только наличие cookie (`getSessionCookie`) и сразу ведёт на `/login?next=`; настоящая проверка — `requireSession()` в layout `(app)`. Путь для `next` layout получает из заголовка `x-request-path`, который ставит proxy.
- `next` проходит через `safeNext`: только путь этого сайта (`/…`, не `//`, не `/\`, без управляющих символов), иначе `/projects`. `/projects` в URL не пишется.
- Письмо отправляет Server Action (`auth.api.signInMagicLink`) с проверкой Zod, а не клиент Better Auth: ошибка показывается под полем по общему образцу форм. Resend через SDK `resend`; без `RESEND_API_KEY` в development и всегда при `MOCK_EXTERNAL=1` ссылка пишется в лог сервера, в production без ключа — ошибка. Пока у Resend нет подтверждённого домена (на `*.vercel.app` его не поставить), в production без `RESEND_API_KEY`/`EMAIL_FROM` `/login` показывает раскладку screens 5.2 целиком, но поле и кнопка email неактивны, у подписи «Email» бейдж «Coming soon», вместо «No passwords…» — «Email sign-in is coming soon. Use GitHub for now.»; войти можно только через GitHub (`isEmailSignInEnabled`). Пустая карточка с одной кнопкой выглядела недоделанной и не вызывала доверия. Форма заработает, как только появятся обе переменные.
- Better Auth отвечает на просроченную, использованную и неизвестную ссылку одним `INVALID_TOKEN`, поэтому любая ошибка ссылки показывает «This link has expired. Request a new one.» (`/login?reason=link-expired`). Ошибка или отмена GitHub — `/login?reason=github`. Параметр не `error`: Better Auth сам ставит `?error=<код>` в `errorCallbackURL` и затёр бы наш.
- Страницы для всех (лендинг, отчёт, 404, `/login`) читают сессию через `getOptionalSession()`: если БД недоступна, страница рисуется как для гостя. На гостевом отчёте вошедший видит шапку приложения, на лендинге — шапку гостя с «Dashboard».
- Тема в меню аватара — группа радио-пунктов прямо в меню, без подменю; `setThemePreference` применяет класс сразу, «System» удаляет значение из `localStorage`.
**Почему:** proxy без обращения к БД дешёвый и убирает мигание защищённой страницы, а проверка в layout закрывает поддельную или истёкшую cookie. Server Action держит валидацию и тексты ошибок на сервере, как у лендинга.
**Альтернативы:** проверка сессии только в proxy (cookie можно подделать, Better Auth прямо это не рекомендует); клиентский `authClient.signIn.magicLink` (валидация и ошибки в двух местах); различать «просрочена» и «уже использована» (Better Auth этого не отдаёт).

### 42. «Check again» перечитывает репозиторий GitHub
**Контекст:** вход отчёта (зависимости, lock-файл, менеджер пакетов) читался из репозитория один раз при создании (decisions 26), и «Check again» проверял старый `package.json`. Для отчёта и проекта из репозитория смысл повторной проверки — текущее состояние репо (spec 6.2).
**Решение:**
- у отчёта с `source = github` «Check again» заново читает `package.json`, `package-lock.json` и признаки менеджера пакетов из `reports.repo_url` тем же путём, что и лендинг (`buildReportInput`), и обновляет `dependencies`, `locked_versions`, `warnings`, `package_manager`, `name` в одной транзакции с созданием проверки. Для гостевого отчёта так же: у него тот же источник и та же кнопка;
- Resume и Retry failed доделывают ту же проверку и репозиторий не читают: иначе внутри одной проверки смешались бы два входа;
- сбой чтения (репо удалён или приватный, нет `package.json`, лимит GitHub, ошибки разбора и лимиты из screens 5.1) — проверка не создаётся, вход не меняется, ошибка показывается тостом теми же текстами;
- отдельный снимок входа на каждую проверку не нужен: `check_packages` уже хранит имя, тип и спецификатор каждого пакета, этого хватает для истории и сравнения в 1.1. Во время повторной проверки строки прошлой проверки берутся только для пакетов из нового входа, чтобы удалённые пакеты не висели до конца проверки.
**Почему:** проверка репозитория без чтения репозитория вводит в заблуждение после каждого пуша; ошибка до старта оставляет пользователю рабочий отчёт.
**Альтернативы:** отдельная кнопка «Pull latest» (лишнее действие, которое почти всегда нужно); чтение репо в начале потока SSE (ошибка чтения превратилась бы в проваленную проверку и стёрла бы прошлую сводку); снимок входа в `checks` (дублирует `check_packages`).

### 43. Импорт репозиториев из GitHub и очередь проверок на дашборде
> Часть про страницу `/projects/import` заменена decisions 48; очередь проверок в силе.

**Контекст:** пользователю с GitHub неудобно добавлять репозитории по одному через `/projects/new`. Автоматически проверять все репо при входе нельзя: десятки репо × сотни запросов, лимит 30 проверок в час (задача 21), форки и не-JS репо дали бы шум, а с уведомлениями (1.2) — спам. При этом проверка идёт только пока открыт поток SSE (decisions 16, 27), фонового запуска нет.
**Решение:**
- проект остаётся единицей отслеживания; импорт — способ быстро создать несколько проектов. Пользователь сам выбирает репо на `/projects/import`, до 10 за раз;
- список: только публичные репо самого пользователя (без организаций), без форков и архивных, 100 последних по push, одним запросом `GET /users/{login}/repos` с серверным `GITHUB_TOKEN`. Токен OAuth пользователя не используется и scope не расширяются: приватные репо вне MVP (spec 10), а публичный эндпоинт приватных не отдаёт. Логин берётся из GitHub-аккаунта пользователя в Better Auth (способ — decisions 47; он же нужен для «Connected as @user» в профиле). Язык не фильтруется: у JS-проектов он бывает Vue, Svelte, HTML;
- наличие `package.json` заранее не проверяется (100 лишних запросов): «Import & check» читает выбранные репо через `buildReportInput` с ограниченной параллельностью и создаёт проекты без проверок; непрочитанные получают ошибку под строкой, остальные создаются. Повторный импорт того же репо этим же пользователем пропускается (метка «Added»);
- проверки запускает очередь на дашборде: клиент открывает поток SSE для проектов без завершённой проверки, не больше 2 одновременно, «Check now» встаёт первым. Лимит проверок считается при старте каждой проверки; упёрлись — карточка показывает «Too many checks. Try again in N minutes.», очередь ждёт. Уход с дашборда останавливает проверки как закрытие отчёта; при возврате очередь продолжает. Открытый проект без проверок запускает первую сам;
- в демо импорт скрыт и `/projects/import` отдаёт 404: у демо-пользователя нет GitHub.
**Почему:** пользователь получает свои репо в пару кликов и сам решает, что мониторить. Очередь на клиенте использует готовый движок (аренда, Resume) без фонового запуска; 2 потока не упираются в лимит соединений браузера и не множат нагрузку на npm.
**Альтернативы:** автоматический импорт и проверка всех репо при входе (стоимость, лимиты, шум); проверка `package.json` у всех репо при показе списка (до 100 запросов на открытие); фоновый запуск проверок (Vercel Workflows или отдельный воркер — decisions 16 откладывает его до замера); вкладка в `/projects/new` вместо отдельной страницы (форма одного проекта и список с множественным выбором плохо уживаются).

### 44. Лимит проверок: окно, счётчик, источник IP

> **Уточнение для [решения 53](#decision-53), реализовано в 26.2:** В задаче 26.2 это решение остаётся правилом часовой защиты, а не правилами новой квоты браузера. Раннее списание, Resume / Retry и учёт отказов относятся только к часовому счётчику. Постоянная квота списывается отдельно и атомарно при создании проверки; ошибка её исчерпания требует отдельного результата действия и CTA входа, а не retryAfter.

**Контекст:** spec 9 — гость не больше 10 проверок в час с одного IP, вошедший — 30 в час, счётчики в основной БД. Проверки запускают Server Actions: лендинг, «Check again», «Resume», «Retry failed» / «Try again» (позже — создание проекта и очередь дашборда, decisions 43). Нужны атомарность при параллельных запросах и надёжный IP за прокси Vercel.
**Решение:**
- фиксированное окно в 1 час, выровненное по началу часа (`windowStart` в `src/server/analysis/rate-limit.ts`): строка `rate_limits` `(subject, window_start)`. Счёт — один запрос `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` (`src/server/db/rate-limits.ts`); `count > limit` → отказ, «Try again in N minutes» до конца окна (N вверх, не меньше 1);
- субъект: `user:<id>` при сессии (30), иначе `ip:<адрес>` (10). Адрес — `x-real-ip`, затем первый адрес `x-forwarded-for`: Vercel перезаписывает `x-forwarded-for` и не пропускает внешние значения, `x-real-ip` ему идентичен (документация Vercel, Request headers). Без заголовков — общий `ip:unknown`;
- одна попытка — одно списание, до тяжёлой работы: на лендинге после разбора формы и до чтения GitHub; в отчёте после проверки id и срока отчёта, до создания или переоткрытия проверки. «Cancel» не считается. Отказ сверх лимита тоже увеличивает счётчик — на решение это не влияет. Ошибка БД на лендинге даёт общую ошибку формы, в отчёте — ошибку действия (как при создании проверки);
- сообщение: на лендинге под полем выбранного источника, в отчёте — тост (`useReportAction`), данные отчёта не меняются. Действия отчёта возвращают `{ error?: string }` только ради лимита;
- проверка, которую создаёт отчёт с лендинга вместе с собой, второй раз не списывается.
**Почему:** фиксированное окно — одна строка на субъекта в час и один атомарный запрос без транзакции и гонок; допускает до 2× всплеск на стыке часов, для защиты бюджета внешних API этого достаточно. Вход меняет субъект на аккаунт, поэтому вошедший не делит лимит с соседями по NAT.
**Альтернативы:** скользящее окно или журнал попыток (точнее, но строка на каждую проверку и выборка при каждом запросе); token bucket (сложнее при той же цели); Upstash / Vercel KV (лишний сервис, spec требует основную БД); `ipAddress` из `@vercel/functions` (лишняя зависимость ради чтения того же заголовка). Строки прошлых окон пока не удаляются — очистка в будущий Vercel Cron.

### 45. Сохранение гостевого отчёта и доступ к отчёту проекта
**Контекст:** задача 22: «Save project» превращает гостевой отчёт в проект (screens 2, 5.4), отчёт проекта открывается на `/projects/[id]/*` теми же компонентами, чужой проект — 404. Гость приходит на `/r/[id]/save` из `next` после входа, вошедший жмёт кнопку на странице.
**Решение:**
- проект получает тот же отчёт (decisions 24): `saveGuestReport` в транзакции с `SELECT … FOR UPDATE` создаёт `projects` (имя из `package.json`, иначе «Untitled project») и ставит отчёту `project_id`, обнуляя `expires_at`. Проверки и результаты остаются, идущая проверка продолжается. Повторное сохранение тем же пользователем отдаёт тот же проект (двойной клик, две вкладки), чужой сохранённый отчёт — «не найден». Лимит проверок не списывается: проверка не создаётся;
- `/r/[id]/save` — GET route handler (303), а не страница: страница, которая пишет в БД при рендере, писала бы и при префетче. Кнопка вошедшего — Server Action `saveReport`, не ссылка на этот адрес, по той же причине. Всё, кроме сохранённого проекта (истёк, чужой, неверный id), ведёт обратно на `/r/[id]/dependencies`, где страница сама показывает «истёк» или 404 с настоящим статусом;
- тост «Project saved» передаётся параметром `?saved=1` (route handler не может вызвать клиентский тост), `ProjectSavedToast` показывает его один раз и убирает параметр без записи в историю;
- доступ — одна чистая функция `canAccessReport` (гостевой отчёт всем, отчёт проекта только владельцу) через `canOpenReport` для текущей сессии. Её проходят layout проекта и гостевой layout, `checkAgain` / `cancel` / `resume` / `retry` (до списания лимита), детали пакета и release notes, поток SSE `/api/checks/[id]/events`. Нет доступа = «не найдено»;
- старая гостевая ссылка сохранённого отчёта: владельцу — редирект на ту же вкладку проекта с тем же query (делает страница вкладки: layout не видит query), остальным — 404;
- один `ReportView` с `mode` (`guest` / `project`): у проекта имя проекта, `basePath` `/projects/[id]`, в шапке «Check again» (основная), «Copy link», иконка «Settings» (страница — задача 24), без строки срока.
**Почему:** тот же отчёт не требует копировать проверки и результаты и сохраняет `check_id` идущей проверки. Проверка доступа в каждом входе, а не только в layout, закрывает действия и поток, которые принимают id напрямую.
**Альтернативы:** копия отчёта и проверок в новый отчёт проекта (дублирование данных, идущая проверка оборвалась бы); страница `/r/[id]/save` с записью при рендере (сохранение при префетче); флеш-cookie для тоста (лишнее состояние на сервере ради одного сообщения); оставить старую ссылку публичной (раскрывает проект).

### 46. Дашборд: очередь проверок на клиенте, снимок для карточки, форма проекта
**Контекст:** задача 23: `/projects` с карточками и очередью проверок (decisions 43), `/projects/new` с RHF + Zod и «Discard changes?» (screens 5.10, 5.11).
**Решение:**
- очередь — чистый редьюсер `features/projects/check-queue.ts` (порядок добавления, «Check now» первым, до 2 активных, пауза всей очереди на лимите до конца окна) и хук `useCheckQueue`, который открывает те же потоки SSE, что и отчёт. Старт проверки — Server Action `queueCheck`: идущую проверку только подхватывает (лимит не списывается), оборванную первую (`cancelled`) продолжает через Resume, проекту без проверок создаёт первую; «Check now» создаёт новую и для GitHub перечитывает репозиторий, как «Check again» (decisions 42);
- «без завершённой проверки» = нет ни одной `completed`/`partial` и последняя не `failed` (`needsFirstCheck`). Проваленную первую проверку очередь не повторяет: карточка пишет «Check failed», повтор — «Check now» или страница проекта. Иначе ошибка источника повторялась бы при каждом открытии. Проект, обработанный за визит, в очередь до «Check now» не возвращается;
- карточке нужен красный цвет при critical/high без загрузки строк: в снимок проверки добавлена колонка `checks.severe_vulnerable_count` (пакеты с худшей уязвимостью critical/high), пишется в `finishCheck` рядом со `score`. У старых проверок `null` — счётчик серый;
- открытый проект без проверок сам запускает первую (`FirstCheckStarter` вызывает `checkAgain` один раз, лимит и ошибка чтения репо остаются на странице с «Try again»). Гостевой отчёт без изменений;
- `/projects/new`: `react-hook-form` + `@hookform/resolvers` (`zodResolver`), Server Action повторяет правила на сервере. Разбор источника вынесен из лендинга в `features/check/prepare-input.ts`. Имя обязательно для Paste/Upload и подставляется из `name` package.json, пока его не правили руками; для GitHub пустое имя → `name` из package.json, иначе имя репозитория. Фокус на поле с ошибкой — через свои refs: `setFocus` RHF после ответа сервера не фокусировал поле;
- «Discard changes?»: перехват кликов по внутренним ссылкам в фазе capture (до `<Link>`), свой диалог; закрытие и перезагрузка вкладки — `beforeunload`. Кнопку «назад» браузера App Router перехватить не даёт — уход без вопроса;
- дашборд лежит в группе `projects/(dashboard)`, чтобы его `loading.tsx` (6 скелетонов) и `error.tsx` не накрывали `/projects/new` и страницы проекта.
**Почему:** очередь на клиенте переиспользует движок проверок (аренда, Resume) без фонового запуска, а чистый редьюсер проверяется unit-тестами. Снимок дешевле, чем читать `check_packages` всех проектов при каждом открытии дашборда.
**Альтернативы:** считать critical/high из `check_packages` при загрузке дашборда (тяжёлый запрос на каждое открытие); повторять failed-проверки в очереди (бесконечные повторы при постоянной ошибке); форма без RHF, как на лендинге (стек требует RHF для форм); `onbeforeunload` без перехвата ссылок (не ловит переходы внутри приложения).

### 47. Настройки проекта и профиля: замена источника, логин GitHub, удаление аккаунта
**Контекст:** задача 24: `/projects/[id]/settings` (имя, «Replace source» с подтверждением, удаление) и `/settings/profile` (имя, email, GitHub, тема, удаление аккаунта) — screens 5.12, 5.13. Нужно решить, как заменить источник, не потеряв историю, откуда взять логин GitHub (он же нужен списку репозиториев в `/projects/new`, decisions 48) и как удалять аккаунт.
**Решение:**
- «Replace source» обновляет тот же отчёт проекта (decisions 24): у `createCheck` появился необязательный `origin` (`source`, `repo_url`), который пишется тем же `UPDATE reports` вместе со входом, в одной транзакции с созданием проверки. Идущая проверка (`already-running`) откатывает всё, источник не меняется. Лимит списывается до чтения источника, как при создании проекта; чужой проект — общая ошибка без списания. История проверок остаётся: это те же `checks` отчёта;
- форма источника (вкладки Paste / Upload / GitHub URL) вынесена из `/projects/new` в `SourceFields`, обе формы держат своё состояние в RHF. В «Replace source» пустое поле ловится до диалога подтверждения;
- логин GitHub не хранится: Better Auth хранит в `account.account_id` числовой id пользователя GitHub, логин читается `GET /user/{id}` с серверным `GITHUB_TOKEN` (`fetchGithubLogin`), ответ проверяется Zod и кэшируется на час (decisions 4). Id не меняется при переименовании, логин всегда актуален. Сбой GitHub не прячет подключение: «Connected to GitHub» без логина;
- «Connect GitHub» — `authClient.linkSocial` с `accountLinking.allowDifferentEmails: true`: у вошедшего по ссылке email GitHub часто другой. Настройка касается только явной привязки, неявное связывание при входе не меняется. Ошибка возвращает на `/settings/profile?reason=github-link` (не `error`, как в decisions 41);
- удаление аккаунта — `auth.api.deleteUser` (`user.deleteUser.enabled`) после ввода email. Без пароля Better Auth требует сессию моложе суток (`freshAge`), иначе `SESSION_EXPIRED` → «sign in again», и кнопка сначала выходит из сессии: `/login` вошедшего сразу уводит на `next`. Проекты, отчёты, проверки, сессии и аккаунты удаляются каскадом, cookie стирает Better Auth. Тост «Account deleted» передаётся параметром `?account-deleted=1`, как «Project saved» (decisions 45);
- доступ к `/projects/[id]/settings` проверяет `layout.tsx` (`loadProjectSettings`, `cache` React на запрос), а не страница: страница сидит внутри `loading.tsx`, и `notFound()` в ней приходил бы после скелетона со статусом 200. Так же устроен layout отчёта проекта;
- тема в профиле — тот же `setThemePreference`, что в меню аватара, без «Save»; начальное значение читается через `useSyncExternalStore` (на сервере «System»).
**Почему:** один отчёт на проект сохраняет историю без копирования, а транзакция не оставляет новый источник без проверки. Id GitHub — стабильный ключ, который Better Auth уже хранит, поэтому не нужны ни миграция, ни поле, которое пользователь мог бы переписать через `updateUser`. Свежая сессия — защита Better Auth от удаления по украденной старой cookie.
**Альтернативы:** новый отчёт при замене источника (история проекта разделилась бы на два отчёта); поле `github_login` в `user` через `mapProfileToUser` (миграция; поле должно принимать ввод, поэтому его можно подменить; у уже вошедших пусто до повторного входа); удаление строки `user` своим запросом без проверки свежести (проще, но обходит защиту Better Auth); письмо с подтверждением удаления (`sendDeleteAccountVerification`, лишний шаг при уже введённом email, а письма в production пока не настроены, decisions 41).

### 48. Список репозиториев GitHub во вкладке `/projects/new` вместо страницы импорта
**Контекст:** decisions 43 вынесла импорт на отдельную страницу `/projects/import` с выбором до 10 репо. На деле пользователь с GitHub попадает в `/projects/new`, видит вкладку «GitHub URL» и вводит URL руками, хотя список его репо доступен. Два входа в одно действие (форма и страница импорта) путают.
**Решение:**
- страницы `/projects/import` нет. Во вкладке «GitHub URL» формы `/projects/new` под полем URL — список своих публичных репо (без форков и архивных, 100 последних по push; логин по id аккаунта, decisions 47, список через серверный `GITHUB_TOKEN` с кэшем). Выбор строки заполняет URL и имя проекта = имя репо, если имя не правили руками;
- один проект за раз: создание и первая проверка идут обычным путём формы (decisions 46);
- «Import from GitHub» на дашборде ведёт на `/projects/new?source=github`;
- список — опциональная часть `SourceFields`, только на `/projects/new`: на лендинге гость не вошёл, в «Replace source» выбор чужого репо из своего списка не нужен (можно добавить позже);
- ошибка или лимит загрузки списка не блокируют форму: URL можно ввести вручную. В демо списка нет.
Остальное из decisions 43 (очередь проверок дашборда) в силе.
**Почему:** один путь создания проекта и один экран меньше; поле URL и список рядом закрывают и чужие репо, и свои.
**Альтернативы:** отдельная страница импорта (decisions 43; два входа); страница импорта плюс список в форме (два списка репо в продукте); множественный выбор в форме (форма одного проекта с полем имени и пакетным созданием плохо уживаются). Цена решения — нет пакетного добавления нескольких репо.
### 49. Список репозиториев GitHub: публичный эндпоинт с серверным токеном и загрузка после страницы
**Контекст:** задача 24.1: список своих публичных репо во вкладке «GitHub URL» на `/projects/new` (screens 5.11.1, decisions 48). Нужно решить, чьим токеном и каким запросом его читать и как не задержать форму, если GitHub медленный или упёрся в лимит.
**Решение:**
- `GET /users/{login}/repos?type=owner&sort=pushed&per_page=100` с серверным `GITHUB_TOKEN` (`fetchGithubUserRepos`); логин — по id аккаунта, как в decisions 47. Форки, архивные и приватные (страховка, как в `fetchRepoSource`) отбрасываются после выборки, поэтому строк может быть меньше 100; пагинации нет. Ответ проверяется Zod и кэшируется на час по `github:repos:<login>` (decisions 4);
- страница знает только, подключён ли GitHub (запрос в БД); сам список загружает Server Action `loadGithubRepos` из браузера при первом открытии вкладки. Состояние загрузки живёт в форме (`useGithubRepos`), а не в панели вкладки: Radix размонтирует неактивную панель, и список перезагружался бы при каждом возврате;
- «Added» — сравнение `owner/repo` без учёта регистра с `repo_url` проектов пользователя (`listProjectRepos`, `markAdded`);
- лимит GitHub показывается текстом «Try again in N minutes» без Retry, прочие ошибки — «Couldn't load your repositories. Retry»; ни то, ни другое не блокирует ручной ввод URL. Поле поиска стоит внутри формы, поэтому Enter в нём не отправляет «Create & check».
**Почему:** публичный эндпоинт отдаёт ровно то, что проверка и так умеет читать (spec 9: только публичные данные), и не требует от пользователя новых OAuth-scope и хранения его токена. Загрузка после страницы оставляет форму рабочей при любом состоянии GitHub.
**Альтернативы:** `GET /user/repos` с OAuth-токеном пользователя (нужен scope и хранение токена, вернёт и приватные); загрузка в Server Component через Suspense (Retry всё равно потребовал бы клиентский запрос); пагинация до всех репо (лишние запросы к лимиту ради редкого случая).

### 50. Демо-аккаунт: вход без пароля, сид как общая функция, блокировки

> **Уточнение для [решения 53](#decision-53), реализовано в 26.2:** Историческое решение задачи 25. В задаче 26.2 отменяются вход через /demo и signInDemo, демо-плашка, автоматический сид и доступ к демо-проектам. Ручной сид и существующие данные сохраняются; защита старых сессий остаётся необходимой.

**Контекст:** задача 25: «Try demo» одним кликом открывает общий демо-аккаунт с 4 проектами из screens 7, плашка закрывается до конца сессии, удаления в демо запрещены, GitHub в демо нет. Нужен вход без ввода данных, сид для скрипта и ежедневного сброса (задача 26) и защита от действий, которые испортят общий аккаунт.
**Решение:**
- демо-пользователь — строка `user` с фиксированным id `demo` (`DEMO_USER`, `isDemoUser`), без отдельной колонки в схеме;
- `/demo` — route handler (как `/r/[id]/save`): если демо-пользователя нет, сначала `seedDemo`, затем `auth.api.signInDemo` — локальный серверный эндпоинт Better Auth (`createAuthEndpoint.serverOnly`, по образцу плагина anonymous: `internalAdapter.createSession` + `setSessionCookie`; cookie в ответ пишет `nextCookies()`) — и 303 на `/projects`. Ссылки на `/demo` — обычные `<a>`: клиентская навигация `<Link>` на route handler проходит редирект без новой cookie и остаётся на месте;
- `seedDemo(db, now)` в одной транзакции под `pg_advisory_xact_lock`: upsert пользователя, удаление его проектов (каскад) и привязанных аккаунтов, вставка проектов, отчётов, завершённых проверок и строк. Данные — чистая `buildDemoProjects(now)` (строки через `buildPackageRow`, даты относительно `now`), снимок проверки — тот же `checkSnapshot`, что у реальной проверки (вынесен из `finishCheck`). Источник — `upload` с `lockedVersions` = текущие версии, чтобы «Check again» не ходил в несуществующий репозиторий и находил те же версии. `pnpm db:seed` запускает её через `tsx`; эту же функцию вызовет cron;
- плашка: сервер не рендерит её, если есть cookie `demo-banner` без срока жизни (умирает с сессией браузера), поэтому нет мигания;
- удаление аккаунта, смена имени, Connect GitHub — кнопки disabled с «Not available in the demo.»; Server Actions `deleteAccount`/`updateName` отказывают демо; `databaseHooks.account.create.before` не даёт привязать аккаунт к демо, прямые эндпоинты Better Auth закрыты хуком (decisions 52). Сид-проекты демо только для чтения, а свои проекты сессии можно удалять: решает условие SQL, а не общий отказ `removeProject` (decisions 52). Без GitHub «Import from GitHub» и список репозиториев скрыты уже существующими условиями;
- лимит проверок демо считается по IP с лимитом гостя (`rateLimitSubject`), а не общий `user:demo`.
**Почему:** одна функция сида держит скрипт, `/demo` и сброс согласованными; снимок через тот же код гарантирует, что дашборд и отчёт показывают одно и то же. Серверный эндпоинт не открывает вход в демо через `/api/auth/*` и не требует пароля в БД.
**Альтернативы:** пароль демо-пользователя и `signInEmail` (секрет в env, лишний провайдер); колонка `is_demo` (миграция ради одного пользователя); сохранять закрытие плашки в `sessionStorage` (мигает при каждой загрузке); общий счётчик лимита (одни посетители съедают лимит других).

### 51. Ежедневная задача: POST с Bearer-секретом, независимые шаги

> **Уточнение для [решения 53](#decision-53), реализовано в 26.2:** В задаче 26.2 шаг demo и поле demo: "reset" в успешном ответе убираются. Остаются два независимых шага guestReports и apiCache с прежними авторизацией, расписанием и обработкой ошибок; постоянная гостевая квота не очищается cron.

**Контекст:** задача 26: `/api/cron/daily` удаляет истёкшие гостевые отчёты, просроченные строки `api_cache` и пересоздаёт демо (decisions 11, 50). Вызывает его workflow `.github/workflows/daily.yml` по расписанию и вручную.
**Решение:**
- `POST` (обработчик меняет данные) с заголовком `Authorization: Bearer <CRON_SECRET>`, сравнение через `timingSafeEqual`. Не задан или пустой `CRON_SECRET` → всегда 401 и запись в лог, чтобы забытая переменная не открыла эндпоинт;
- граница истечения `expires_at <= now` — та же, что у `isReportExpired`: cron удаляет ровно то, что страница отчёта уже показывает как истёкшее. Отчёты проектов не попадают: у них `expires_at` NULL. Проверки и строки пакетов удаляются каскадом;
- три шага с одним `now` выполняются независимо: сбой одного пишется в лог и не отменяет остальные. Если упал хоть один — 500 со списком шагов, `curl --fail-with-body` делает запуск workflow красным;
- расписание 03:00 UTC, `APP_URL` — переменная репозитория, `CRON_SECRET` — секрет GitHub и переменная Vercel.
**Почему:** секрет в заголовке не попадает в логи URL; независимые шаги не дают сбою сида оставить кэш неочищенным, а красный запуск виден в Actions.
**Альтернативы:** `GET` как у Vercel Cron (мутация на GET, а Vercel Cron не используется); общая транзакция на все шаги (сбой одного откатывает остальные без причины); секрет в query (оседает в логах).

### 52. Демо от хулиганов: хук Better Auth, проекты на сессию, лимит magic link

> **Уточнение для [решения 53](#decision-53), реализовано в 26.2:** История реализованной задачи 26.1. В задаче 26.2 доступ демо к сид-проектам и проектам своей сессии, создание проектов и запуск проверок отменяются. Разрешение server-only signInDemo больше не требуется. Защиту прямых auth-эндпоинтов и старых сессий не снимать; выход и обычный вход сохранить. Лимиты magic link на IP и email остаются без изменений.

**Контекст:** задача 26.1: демо-аккаунт один на всех посетителей. Через `/api/auth/*` можно было сменить имя и `image` демо (аватар в шапке у всех), удалить его (`/delete-user`: сессия демо свежая и без пароля, проходит мимо `deleteAccount`), прочитать чужие сессии (`/list-sessions`, IP и User-Agent) и выкинуть всех (`/revoke-*`). Проекты демо общие: переименование и замена источника видны всем. Ссылки входа можно было слать без ограничений.
**Решение:**
- `hooks.before` в `auth.ts` с **разрешённым** списком путей для демо (`isDemoAuthPathAllowed`): `/get-session`, `/sign-out`, `/sign-in/*`, `/magic-link/verify`, `/callback/*`, `/ok`, `/error` и server-only эндпоинты без пути (`signInDemo`). Для них сессия не читается; остальное при сессии демо → 403. Хук срабатывает и на вызовы `auth.api.*`. Второй слой — `databaseHooks.user.update.before` / `delete.before` → `false` для демо. В 1.7.12 `update.before` получает только изменяемые поля без id, поэтому демо узнаётся по `ctx.context.session`;
- колонка `projects.demo_session_id` (FK на `session`, `on delete cascade`, миграция 0004). Сид — `null`. Одно правило `projectAccess` (`src/server/analysis/project-access.ts`): не демо — владелец пишет; демо — сид `read`, проект своей сессии `write`, чужой сессии `none`. Его SQL-двойники `visibleProjects` / `editableProjects` (`src/server/db/project-access.ts`) стоят в WHERE всех запросов `projects.ts`, `canAccessReport` вызывает то же правило. Id сессии берётся из cookie (`viewerOf(session)`), не из запроса. Удаление, переименование и замена источника идут с `owner_id = 'demo' AND demo_session_id = <своя сессия>` (не `IS NULL`), поэтому сид и проекты других сессий не меняются при любом присланном id. Check now / Check again на сид-проектах работают (лимит по IP, decisions 50). Истёкшая сессия удаляет свои проекты каскадом, ежедневный сброс — все проекты демо;
- лимит ссылок входа в `rate_limits`: 10 в час на IP (`magic-ip:<адрес>`), затем 3 за 15 минут на email (`magic-email:<email>`), фиксированные окна, как в decisions 44 (`windowStart` получил длину окна). Проверка внутри `sendMagicLink`, поэтому прямой `POST /api/auth/sign-in/magic-link` тоже под лимитом. Отказ — `APIError` 429 с кодом `MAGIC_LINK_RATE_LIMITED` и текстом «Too many requests. Try again in N minutes.», `sendSignInLink` показывает его под полем. IP считается первым: за лимитом IP счётчик email не тратится. Поверх этого в production работает встроенный лимит плагина magic-link (в памяти процесса, 5 в минуту с IP): он гасит всплески, но не переживает холодный старт функции и не ограничивает час.
**Почему:** разрешённый список закрывает и эндпоинты, которые появятся в следующих версиях Better Auth или плагинах. Проекты на сессию дают посетителю попробовать создание и удаление проекта, не трогая данные других, ценой одной nullable-колонки.
**Альтернативы:** запрещённый список путей (новый эндпоинт открыт по умолчанию); демо целиком только для чтения (нельзя попробовать главный сценарий — создать проект); копия демо-пользователя на каждого посетителя (строки `user` и сид из 4 проектов на каждый клик «Try demo», очистка пользователей); лимит magic link в `sendSignInLink` (прямой запрос к `/api/auth` его обходит).

### 53. Гостевые проверки вместо демо-доступа
**Статус:** реализовано и проверено 25.10.2026; принято автором для коммита. Поведение: [spec 9.1](spec.md#guest-quota); интерфейс: [screens 4.3](screens.md#guest-quota-ui); порядок реализации: [plan 26.2](plan.md#task-26-2).

**Контекст:** после защиты общего демо в 26.1 остаётся отдельный сложный сценарий с общими данными и сессиями. Лендинг уже умеет Paste / Upload / GitHub URL и sample project. Для знакомства с продуктом достаточно трёх обычных гостевых запусков на браузер, затем входа.

**Решение:**
- Постоянный счётчик использованных запусков в отдельной таблице БД, не в оконных строках `rate_limits`. Cookie содержит случайный непрозрачный идентификатор браузера, а не остаток; постоянная (с явным сроком), HttpOnly, SameSite=Lax, Secure в production. Счётчик не имеет периодического сброса и не удаляется вместе с отчётом или при cron. Очистка/утрата cookie позволяет начать заново — допустимо для MVP, это не строгая идентификация человека.
- До запуска получить идентичность браузера на сервере и проверить остаток, чтобы при нуле не читать GitHub. Клиент не передаёт доверенный остаток или владельца квоты. При нескольких первых запросах идентификатор должен быть установлен до разрешения запуска в UI; проверить отдельным сценарием инициализацию без cookie. Часовую защиту проверять отдельно по прежним правилам решения 44.
- После успешной подготовки входа условное атомарное списание при остатке больше нуля и создание `checks` выполняются в одной транзакции. Для первого запуска она включает `reports`, для Check again — обновление входа отчёта. При одной попытке параллельные транзакции создают не больше одной проверки; отказ, ошибка БД или `already-running` откатывают списание и изменения входа. Не списывать в отдельной транзакции с последующим «возвратом».
- Новая проверка считается израсходованной после commit, даже если SSE ещё не открылся, соединение оборвалось, пользователь нажал Cancel или источники дали ошибки пакетов. Resume / Retry failed / Try again существующей проверки, открытие SSE и переподключение не расходуют постоянную квоту; часовая защита Resume / Retry сохраняется.
- Квота принадлежит браузеру инициатора запуска, не отчёту и не его автору. Все три источника, пример и повтор одного репозитория делят три попытки. Публичный отчёт доступен до истечения семи дней при любом остатке; после истечения или удаления отчёта квота не восстанавливается.
- Обычный вошедший пользователь на лендинге и в отчёте использует только прежний лимит аккаунта (30 в час). Вход/выход не меняют гостевой счётчик. При исчерпании квоты возвращать отдельный различимый результат действия с актуальным остатком для UI; не выдавать его за часовой rate limit с временем ожидания. Ошибки чтения/записи квоты не разрешают запуск без учёта и не показываются как исчерпание; использовать существующую общую ошибку с повтором.
- UI и OAuth следуют screens 4.3: счётчик, CTA GitHub, безопасный локальный адрес возврата с query, без автозапуска и автосохранения. Email-вход и защита magic link из 26.1 остаются. Подстановка sample project бесплатна, запуск — обычная попытка.
- `/demo` возвращает 404 и не создаёт сессию или данные; server-only демо-вход отключается. Старый `user.id = demo` не считается обычным вошедшим пользователем и не получает лимит аккаунта. Старые cookie не дают доступа к проектам (включая сид и проекты своей сессии), связанным отчётам, SSE, сохранению гостевого отчёта в демо и действиям аккаунта. Защита нужна на сервере: страницы, Server Actions, route handlers и прямые Better Auth endpoints; скрытых кнопок недостаточно. Сохраняются выход и обычный вход, публичные гостевые страницы могут работать без демо-привилегий.
- Cron оставляет только удаление истёкших гостевых отчётов и `api_cache`; убрать вызов `seedDemo`, результат `demo: "reset"` и упоминание сброса в комментарии workflow. Ручной `pnpm db:seed` остаётся вспомогательным инструментом. Старые данные, миграции и `projects.demo_session_id` не удаляются; рефакторинг демо-инфраструктуры и удаление данных не входят в задачу.

**Точки реализации:** `startGuestCheck` / `createGuestReport`, `checkAgain` / `createPgCheckStore.createCheck`, серверная идентификация и слой квоты. Не добавлять чтение cookie и SQL в `check-control`; контекст квоты передавать в серверный слой транзакции. Проверить все пути создания проверок и доступа, не ограничиваться лендингом. Миграция только добавляет хранилище квоты; применение к БД — отдельное согласованное действие.

**Почему:** атомарность исключает превышение квоты и потерю попытки при ошибке подготовки; отдельный счётчик сохраняет часовую защиту и не восстанавливается при очистке отчётов. Закрытие старых сессий позволяет отказаться от демо без удаления данных.
**Альтернативы:** счётчик в cookie/localStorage (клиент меняет остаток); квота по IP (общая для разных людей); восстановление каждый день (противоречит трём запускам всего); списание до подготовки с компенсацией (дополнительные гонки и риск потери попытки).

**Проверки реализации:** unit на правила квоты и различимые исходы; интеграция с PostgreSQL на параллельное последнее списание, commit/rollback, ошибки подготовки и `already-running`; проверки всех точек доступа со старой демо-cookie; RTL на остаток, ноль и CTA; e2e на три запуска одного репозитория, отказ четвёртого, новое посещение, Resume / Retry при нуле, отмену, GitHub-вход с возвратом и выход, доступ к готовому отчёту и квоту другого браузера. Проверить cron без демо-шага и сохранение защиты magic link. Существующие демо-тесты заменить проверками закрытого доступа, а не просто удалить покрытие.


**Детали реализации 26.2:**
- `guest_quotas(id UUID PRIMARY KEY, used INTEGER CHECK 0..3)` не связана внешним ключом с отчётом или аккаунтом. Чтение отсутствующей строки означает три доступных запуска; строка создаётся при первом списании.
- Cookie `radar-guest` устанавливается в proxy при GET лендинга/гостевого отчёта, передаётся серверному рендеру и браузеру. UUID v4, HttpOnly, SameSite=Lax, Path=/, Secure в production; срок 400 дней продлевается при посещениях с тем же id. POST без корректной cookie не получает новую идентичность и не запускает проверку.
- Перед подготовкой источника проверяется остаток. В транзакции условный UPDATE при `used < 3` сериализует списания одного браузера. Исключение при исчерпании, ошибке БД или конфликте запущенной проверки откатывает списание и изменения отчёта. В CheckStore передаётся серверный id инициатора; Resume/Retry используют хранилище без контекста списания.
- Server Actions различают `guest-quota-exhausted` с остатком 0 и часовую ошибку. Общий UI квоты обновляется после действий и при возврате во вкладку; сбой чтения блокирует только новый запуск и предлагает Retry. GitHub CTA сохраняет текущие путь/query; подсказка сохранения ограничена явным `/r/[id]/save`.
- Старые демо-сессии фильтруются на границе авторизации; правила доступа и SQL-предикаты также запрещают их проекты. Демо-вход не регистрируется в Better Auth. Прежний auth allowlist и защита magic link остаются; server-only пути больше не разрешены демо.
- Интеграционные тесты запускаются отдельно через `pnpm test:integration`, требуют явную `TEST_DATABASE_URL` и применяют миграции только к указанной тестовой БД. В CI используется отдельный PostgreSQL service. OAuth e2e подменяет внешнего провайдера и создаёт тестовую сессию; реальный GitHub OAuth требует отдельной проверки с настроенным приложением.

**Дополнение 26.2 — пауза повторных проверок:**
- Для всех пользователей новые проверки одного `reportId` разделены 60 секундами от `checks.started_at`. Сохранение гостевого отчёта сохраняет этот идентификатор и паузу. Новый отчёт, даже с тем же источником, независим. Отмена не возвращает попытку и не сбрасывает паузу; Resume / Retry / SSE её не расходуют и не продлевают. Первый запуск доступен сразу.
- Используем существующую историю и индекс `(report_id, started_at)`, без миграции и отдельного счётчика. Альтернатива — таймер в браузере — не защищает от нескольких вкладок; отдельная таблица не нужна при наличии истории проверок.
- После проверки доступа предварительный отказ идёт до часовой защиты и GitHub. В `createCheck` блокируем строку отчёта `FOR UPDATE`, повторно проверяем running и срок, затем списываем гостевую квоту и записываем вход/проверку в одной транзакции. Время новой проверки берётся после ожидания блокировки. Ошибки откатывают всё и не начинают новую паузу. Прежняя часовая защита сохраняется, включая проигравшие гонку запросы после её списания.
- Исход `check-cooldown` несёт абсолютный `nextCheckAt` в хранилище и Server Actions. Check again, Check now и Replace source используют его одинаково; движок не знает cookie или SQL. UI показывает отсчёт и обновляется при возвращении во вкладку; окончание таймера никогда не запускает проверку. Отказ очереди завершает только этот элемент без автоматического повтора.

### 54. Сквозное состояние сети и повтор запросов

**Контекст:** задача 27, spec 8 и screens 4.4–4.5. Потеря сети не должна скрывать загруженный отчёт, терять ввод или оставлять пользователя без возможности повторить запрос.

**Варианты:** периодический запрос к серверу; локальное состояние сети в каждом экране; общий хук браузерного состояния с подпиской на события.

**Решение:** общий клиентский хук на React useSyncExternalStore читает navigator.onLine и события online/offline. Серверный snapshot — online для согласованной гидратации. Это сигнал браузера, а не проверка доступности API: отклонения запросов обрабатываются отдельно у соответствующего действия. Опрос сервера не нужен.

- Баннер над шапкой использует точный текст screens 4.5. Только сетевые действия получают блокировку, подпись причины и проверку в обработчике; локальное редактирование, sample, фильтры, выбор файлов, тема и копирование доступны.
- Загрузчики сохраняют готовые данные, а ещё не выполненные чтения показывают офлайн-состояние вместо бесконечного скелетона. Отложенные чтения продолжаются при подключении; завершившиеся ошибкой повторяются вручную.
- Существующий EventSource сохраняет штатное переподключение. Новые подключения и ожидающие элементы уже созданной очереди ждут сеть. Ошибка отправленной операции не ставит её на автоматический повтор: формы, Check again и ручные действия повторяются только пользователем. Серверные квоты и cooldown остаются источником истины.
- Ошибка запроса остаётся рядом с действием и имеет Retry. Прежние тосты ошибок, предусмотренные экранами, сохраняются, но не служат единственным способом повтора. Повтор удаления остаётся внутри диалога с проверкой введённого имени/email. Обычные тосты — 5 секунд, с действием — 8 секунд, как в существующем компоненте.

**Почему:** единый сигнал не требует зависимости или сетевого heartbeat; восстановление сети не дублирует мутации. Это не offline-first режим: перезагрузка страницы без сети и сохранение данных между посещениями не поддерживаются.
