# Решения по стеку (docs/decisions.md)

Каждый пункт — готовый ответ на вопрос «почему вы выбрали X?» на собеседовании. Новые решения дописывайте в том же формате.

---

### 1. Next.js App Router
**Контекст:** нужны лендинг с хорошим SEO и быстрым первым экраном, приложение за авторизацией и серверная часть для обращения к внешним API.
**Решение:** Next.js App Router.
**Почему:** фронт и сервер в одном проекте, Server Components отдают данные без лишнего JS на клиенте, Server Actions подходят для мутаций, route handlers — для стриминга прогресса. Это самый востребованный стек в вакансиях с React.
**Альтернативы:** Vite SPA + отдельный бэкенд (два деплоя, хуже SEO лендинга), Remix / React Router 7 (тоже подходит, но меньше спрос в вакансиях).

### 2. PostgreSQL (Neon) + Drizzle ORM
**Контекст:** данные реляционные: пользователи, команды, проекты, проверки, пакеты, кэш внешних ответов.
**Решение:** Postgres на Neon, Drizzle как ORM.
**Почему:** у Neon есть бесплатный тариф, он serverless и интегрируется с Vercel. Drizzle полностью типизирован, запросы близки к SQL (видно, что выполняется), он лёгкий и не требует отдельной генерации клиента.
**Альтернативы:** Prisma (тяжелее, но популярнее), Supabase (сразу БД и авторизация, но сильнее привязывает к платформе).

### 3. Better Auth
**Контекст:** нужны вход через GitHub и по ссылке на email, а позже команды и роли.
**Решение:** Better Auth.
**Почему:** TypeScript-first, работает с Drizzle, есть плагины для magic link и организаций (команды и роли). Сессии хранятся в нашей БД, без внешнего сервиса.
**Альтернативы:** Auth.js (с 2025 года развивается командой Better Auth), Clerk (быстро, но платный сервис и чужой UI).
**Проверить при старте:** актуальность плагинов magic link и organization в документации Better Auth.

### 4. Кэш внешних API в Postgres
**Контекст:** у GitHub API есть лимит запросов, а проверка проекта делает сотни запросов.
**Решение:** таблица кэша (ключ, ответ, срок жизни) в той же БД, TTL 1 час, ограниченная параллельность запросов.
**Почему:** не нужен отдельный сервис (Redis), повторная проверка выполняется мгновенно, лимиты не исчерпываются.
**Альтернативы:** Redis (Upstash) — быстрее, но это ещё один сервис; кэш Next.js `fetch` — менее прозрачный и плохо контролируемый.

### 5. Прогресс проверки через SSE
**Контекст:** проверка занимает секунды, и пользователь должен видеть прогресс и частичные результаты (ТЗ 6.2).
**Решение:** Server-Sent Events из route handler.
**Почему:** поток идёт в одну сторону (сервер → клиент), SSE проще WebSocket, работает по обычному HTTP и переподключается сам.
**Альтернативы:** polling (проще, но с задержкой и лишними запросами), WebSocket (избыточен для однонаправленного потока).

### 6. Состояние фильтров в URL (nuqs)
**Контекст:** ТЗ требует, чтобы ссылка открывала ту же выборку таблицы.
**Решение:** фильтры, сортировка, поиск и открытый пакет хранятся в search params через nuqs.
**Почему:** типизированные search params, работает и в Server, и в Client Components, состояние можно передать ссылкой.

### 7. TanStack Table + TanStack Virtual
**Контекст:** таблица с 500+ строками, сортировкой, фильтрами и массовым выделением.
**Решение:** headless-таблица TanStack и виртуализация строк.
**Почему:** логика таблицы без навязанной вёрстки (разметку и доступность контролируем сами), виртуализация держит отзывчивость при больших списках.

### 8. Zod везде на границах
**Решение:** одна схема Zod для формы, Server Action и ответов внешних API.
**Почему:** внешним данным нельзя доверять. Валидация на границе даёт типы и понятные ошибки, а не падение глубоко в коде.

### 9. Чистая логика анализа отдельно от I/O
**Решение:** расчёт отставания, оценки здоровья, поиск breaking changes и построение плана — чистые функции в `src/server/analysis`.
**Почему:** их легко покрыть unit-тестами без сети и БД. Это самая важная логика продукта.

### 10. Тесты: Vitest + Testing Library + MSW + Playwright
**Почему:** Vitest быстрый и совместим с API Jest. Testing Library тестирует поведение, а не реализацию. MSW подменяет внешние API на уровне сети, поэтому тесты не зависят от npm и GitHub. Playwright прогоняет ключевые сценарии ТЗ в настоящем браузере в CI.

### 11. Vercel + GitHub Actions, задачи по расписанию через GitHub Actions
**Контекст:** уже в MVP нужна ежедневная задача: физически удалить гостевые отчёты старше 7 дней и сбросить демо-аккаунт. В 1.2 добавятся регулярные проверки проектов.
**Решение:** деплой на Vercel (превью на каждый PR, бесплатный тариф). CI в GitHub Actions проверяет lint, типы, unit- и e2e-тесты до мержа. Задачи по расписанию запускает workflow GitHub Actions (`schedule`), который вызывает route handler `/api/cron/daily`, защищённый секретом в заголовке.
**Почему:** не зависим от лимитов Vercel Cron на бесплатном тарифе, расписание и логи запусков лежат в репозитории рядом с CI. Истечение гостевого отчёта проверяется при каждом открытии, поэтому корректность не зависит от того, отработала ли задача: она только чистит данные. В 1.2 тот же механизм запускает регулярные проверки.
**Альтернативы:** Vercel Cron (ограничен на бесплатном тарифе), внешний cron-сервис (ещё одна зависимость).
**Проверено при старте:** лимит длительности функции Vercel достаточен, проверка остаётся внутри SSE route handler (раздел 16).

### 12. Geist + дизайн-токены в теме Tailwind
**Контекст:** нужен строгий чёткий шрифт уровня SF Pro и единый стиль на всех экранах, которые пишутся с помощью AI-агента.
**Решение:** Geist Sans / Geist Mono (пакет `geist`) и все цвета, размеры и скругления как токены в `docs/design/theme.css` (Tailwind v4, имена переменных как в shadcn/ui).
**Почему:** SF Pro по лицензии Apple нельзя встраивать в сайт. Geist бесплатный (OFL), хорошо читается в мелких размерах, моноширинная пара подходит для версий пакетов. Токены не дают стилю расползаться: компоненты используют `bg-card`, `text-danger`, а не случайные hex-цвета; тёмная и светлая тема переключаются одним классом.
**Альтернативы:** Inter (более нейтральный), отдельный дизайн-файл в Figma (точнее, но его нельзя проверить автоматически и легко рассинхронизировать с кодом).

### 13. Тема: свой inline-скрипт в `<head>`
**Контекст:** тема по умолчанию System, переключение классом `.dark` на `<html>`, без мигания при загрузке (стайлгайд, раздел 8).
**Решение:** скрипт из `src/lib/theme.ts` вставляется в `<head>` корневого layout и до отрисовки ставит `.dark` и `color-scheme` по значению `theme` в `localStorage` (`light` / `dark` / `system`). При System скрипт следит за сменой системной темы. Если хранилище недоступно или значение неизвестно, используется System.
**Почему:** это около 20 строк без зависимостей. Тест выполняет ту же строку, которая уходит в браузер, поэтому тест и код не расходятся.
**Альтернативы:** `next-themes` (готовое решение, но ещё одна зависимость вне стека ради одной функции).

### 14. Версии инструментов: TypeScript 5 и ESLint 9
**Контекст:** при старте уже вышли TypeScript 7 и ESLint 10.
**Решение:** TypeScript `^5`, ESLint `^9`.
**Почему:** так ставит create-next-app 16.4. Плагины внутри `eslint-config-next` (react, jsx-a11y, import) объявляют совместимость только до ESLint 9, а совместимость TypeScript 7 с typescript-eslint не проверена.
**Альтернативы:** последние мажорные версии — получаем предупреждения о несовместимых зависимостях и риск сломанного lint.

### 15. Дополнительные dev-зависимости: `eslint-config-prettier`, `@testing-library/jest-dom`
**Контекст:** CLAUDE.md разрешает только зависимости из списка стека.
**Решение:** добавлены две dev-зависимости, обе одобрены автором.
**Почему:** `eslint-config-prettier` отключает правила ESLint, которые спорят с Prettier, иначе `lint` и `format` противоречат друг другу. `@testing-library/jest-dom` даёт матчеры `toBeInTheDocument`, `toHaveClass`, `toHaveAttribute` для проверок доступности в RTL-тестах.
**Альтернативы:** ручные проверки через `expect(el.getAttribute(...))` (многословнее и хуже сообщения об ошибках).


### 16. Длительность проверки на Vercel: проверка внутри SSE route handler
**Контекст:** проверка выполняется в SSE route handler (раздел 5), а в лимит длительности функции Vercel входит и время стриминга ответа. По таймауту Vercel обрывает запрос с 504 `FUNCTION_INVOCATION_TIMEOUT`. Нужно понять, укладывается ли проверка 300 пакетов в этот лимит.
**Факты (документация Vercel, fluid compute включён по умолчанию):** на Hobby 300 с по умолчанию и максимум. На Pro по умолчанию тоже 300 с, но можно поднять до 800 с.
**Оценка:** ТЗ требует, чтобы 100 пакетов проверялись не дольше 30 с, то есть 300 пакетов (максимум) — около 90 с без кэша. Запас примерно в 3 раза.
**Решение:** проверка идёт внутри SSE route handler, у handler `export const maxDuration = 300`. Каждый результат пакета сразу пишется в БД, поэтому при обрыве (таймаут, закрытая вкладка) Resume доделывает только непроверенные пакеты.
**Почему:** один запрос вместо двух и нет механизма фонового запуска и опроса прогресса. Худший случай — таймаут — уже покрыт Resume.
**Альтернативы:** проверка отдельным запросом с прогрессом в БД, SSE только читает (сложнее, нужен фоновый запуск); Vercel Workflows (ещё одна платформенная зависимость). Переходим на них, если реальный замер 300 пакетов (задача 29) окажется дольше 200 с.

### 17. UI-примитивы: `radix-ui` одним пакетом, clsx + tailwind-merge + cva
**Контекст:** нужны доступные Dialog, Popover, DropdownMenu, Tooltip, Tabs и Toast, а также единый способ описывать варианты компонентов (Button, Badge) и объединять классы.
**Решение:** пакет `radix-ui` целиком, а не `@radix-ui/react-*` по отдельности. Варианты описываются через `class-variance-authority`, классы объединяются функцией `cn` из `src/lib/cn.ts` (`clsx` + `tailwind-merge`). Все три зависимости одобрены автором.
**Почему:** документация Radix рекомендует единый пакет: он поддерживает tree-shaking и исключает расхождение версий отдельных примитивов. С tailwind-merge `className` снаружи корректно перебивает классы варианта (например, `h-8` вместо `h-9`). tailwind-merge знает только тему по умолчанию, поэтому в `cn` ему передаются наши размеры текста (`2xs`, `md`, `hero`) и `shadow-overlay`. Без этого `text-hero` считается цветом, и рядом с `text-sm` остаются оба класса. Этот список нужно поддерживать вместе с `globals.css`.
**Альтернативы:** своя `cn` без зависимостей (тогда конфликтующие классы из `className` не перебиваются); отдельные пакеты `@radix-ui/react-*`.

### 18. Разбор `package.json`: какие зависимости считаются и как возвращаются ошибки
**Контекст:** в таблице у пакета только два типа (основная или dev), а сообщения об ошибках ввода (screens 5.1) должны быть одинаковыми для Paste, Upload и GitHub URL.
**Решение:** `parseManifest` (`src/server/analysis/parse-manifest.ts`) учитывает только `dependencies` и `devDependencies`. Пакет из обоих разделов считается один раз, как основной. Ошибки возвращаются кодами с данными (`line`, `max`, `maxBytes`, `format`) без текста, а тексты лежат в `src/features/check/copy.ts`: там тип требует текст для каждого кода. JSON, который не похож на `package.json` (корень не объект, версия не строка), получает отдельное сообщение «This doesn't look like a valid package.json.» (spec 8). Номер строки невалидного JSON берётся из сообщения V8 (`line N` или `position N`); если его нет, строка не показывается.
**Почему:** npm сам ставит версию из `dependencies`, если пакет указан в обоих разделах. Коды вместо текста оставляют логику чистой и позволяют позже перевести интерфейс (spec 9).
**Альтернативы:** учитывать `peerDependencies` и `optionalDependencies` (в таблице для них нет типа); бросать исключения с текстом (логика смешивается с копирайтом).

### 19. Lock-файлы: только `package-lock.json` v2/v3, отдельный лимит, распознавание чужих форматов
**Контекст:** реальные lock-файлы часто весят 1–5 MB, а пользователь может вставить lock-файл вместо `package.json`.
**Решение:** `parseLockfile` читает только `package-lock.json` v2/v3 с лимитом 10 MB (у `package.json` 1 MB). Битый, слишком большой или v1 lock-файл проверку не останавливает: вызывающий код продолжает по диапазонам (max satisfying) и показывает предупреждение. `detectLockfile` распознаёт lock-файл по содержимому без разбора: `# yarn lockfile v1` в тексте → yarn v1; первая значимая строка `__metadata:` → yarn berry, `lockfileVersion:` → pnpm (сначала пропускаются BOM, пустые строки, `#`-комментарии и маркер `---`); JSON с ключом `lockfileVersion` → npm. Распознавание идёт до проверки размера и JSON, поэтому для Paste и Upload сообщение будет «This is a lockfile…». Подсказка «add the lockfile in Upload» показывается только для npm.
**Почему:** проверка не должна падать из-за необязательного файла. «This is a lockfile» полезнее, чем «invalid JSON» или «too large». Признаки сверены с настоящими файлами (npm/cli, yarnpkg/berry, vuejs/core, vitejs/vite, этот репозиторий): lockfile v9 у pnpm 9+ начинается с `---`, а не с `lockfileVersion:`.
**Альтернативы:** общий лимит 1 MB (отсекает обычные lock-файлы); ошибка при битом lock-файле (лишний шаг для пользователя); разбор `pnpm-lock.yaml` / `yarn.lock` (нужен YAML-парсер, отложено).

### 20. Классификация спецификаторов (spec 7.4)
**Контекст:** нужно отличать версии из реестра от git, локальных путей и протоколов менеджеров пакетов.
**Решение:** `classifySpecifier` сначала разбирает `npm:<имя>@<спецификатор>` (без версии → `*`; вложенный алиас или не-реестровый спецификатор → invalid). Затем идёт список префиксов, которые не проверяются (`git+`, `git:`, `github:`, `gitlab:`, `bitbucket:`, `file:`, `link:`, `workspace:`, `portal:`, `patch:`, `catalog:`, `http(s):`, локальные пути) и шорткат `owner/repo`. Потом `semver.validRange`, потом правило имени тега.
**Почему:** порядок повторяет npm: диапазон важнее тега. `catalog:` у pnpm ведёт в реестр, но версию по одному `package.json` не узнать, поэтому такой пакет помечается «Not checked».
**Альтернативы:** `npm-package-arg` (новая зависимость ради одной функции).

### 21. Версии, отставание и статус пакета
**Контекст:** spec 3, 7.3 и screens 5.5 задают текущую и последнюю версию, отставание и статусы, но не говорят, что делать с пререлизами, 0.x и версиями, помеченными deprecated по отдельности.
**Решение:** `analyzePackage` (`src/server/analysis/analyze-package.ts`) и функции под ним:
- текущая версия берётся из lock-файла, даже если она не подходит под диапазон. Если записи в lock-файле нет или версия в ней не semver, берётся `semver.maxSatisfying` по диапазону, а тег разрешается через `dist-tags`;
- последняя версия — тег `latest`. Если он указывает на пререлиз или на версию, которой нет в `versions`, берётся максимальная стабильная версия. Если стабильных версий нет, пакет помечается «Not checked» с причиной `no-stable-version`;
- отставание считается по компонентам major/minor/patch строго по semver: 0.2 → 0.3 — minor. Пререлиз последней версии (1.0.0-rc → 1.0.0) — patch, текущая версия новее последней — up to date. `semver.diff` не используется: он считает 1.0.0-rc → 1.0.0 мажорным;
- deprecated — только если помечена последняя стабильная версия (spec 7.1). Deprecated важнее stale;
- последний релиз — самая поздняя публикация любой версии (включая пререлизы и бэкпорты) из `time`. Ключи `created`/`modified` и снятые с публикации версии не учитываются. Stale — если с последнего релиза прошло строго больше 12 календарных месяцев (UTC); текущее время передаётся параметром;
- причины «Not checked» возвращаются кодами (`not-from-registry`, `invalid-specifier`, `no-matching-version`, `unknown-tag`, `no-stable-version`), тексты будут в UI.
**Почему:** lock-файл — факт установки, диапазон — только предположение. Устаревшая старая версия значит «обновись», а это уже показывает отставание; пометка на последней версии значит, что автор бросил пакет. 0.x по semver совпадает с цифрами, которые видит пользователь. Пакет, который выпускает только пререлизы или бэкпорты, жив, поэтому он не stale.
**Альтернативы:** приоритет `latest`, если он подходит под диапазон (так делает npm при установке, но spec 3 говорит «максимальная подходящая»); 0.x по правилам caret (0.2 → 0.3 = major); deprecated и по установленной версии; дата релиза только версии `latest`.

### 22. Уязвимости: объединение записей OSV, «Fixed in» и критичность
**Контекст:** spec 7.1 и 7.3 требуют объединять записи OSV по `aliases`, брать высшую критичность и показывать «Fixed in» — наименьшую версию, исправленную по всем записям. Но spec не говорит, откуда брать версии-кандидаты, что делать с записями без метки критичности и как читать диапазоны `affected`.
**Решение:** `mergeVulnerabilities` (`src/server/analysis/merge-vulnerabilities.ts`):
- записи объединяются через union-find по `id` и `aliases`, транзитивно. Две записи связываются и через общий алиас, которого нет среди полученных записей (две GHSA с одним CVE). Записи с `withdrawn` пропускаются. В `ids` попадают ID записей и их алиасы, по порядку: GHSA, CVE, остальные, затем по алфавиту. Первый ID основной, его описание показывается;
- «Fixed in»: кандидаты — только события `fixed` из диапазонов `SEMVER`/`ECOSYSTEM` этого пакета (`affected` фильтруется по `npm` и имени), строго выше текущей версии. Ответ — наименьший кандидат, который не затронут ни одной записью (учитываются `introduced`, `fixed`, `last_affected` и список `versions`). Если такого нет — `null` («No fix available»);
- критичность записи (`src/server/analysis/severity.ts`): `MAL-*` → critical; метка GHSA `database_specific.severity` → её значение; иначе базовая оценка из вектора CVSS v3.0/3.1 (≥ 9 critical, ≥ 7 high, ≥ 4 moderate, иначе low); иначе moderate. Формула CVSS v3 написана своими силами по спецификации FIRST, CVSS v4 не считается.
**Почему:** версия из события `fixed` точно была выпущена как исправление, а для `last_affected` и списка `versions` следующую опубликованную версию без данных реестра не узнать. Метка GHSA есть почти у всех npm-записей. Вредоносный пакет (MAL) хуже любой уязвимости. Moderate для записи без данных учитывает её в оценке, но не делает её главной. Тексты и ссылки на источники будут в UI.
**Альтернативы:** минимальная из версий исправления (неверно, если другая запись ещё затрагивает эту версию — spec 7.3); кандидаты из списка версий реестра (точнее для `last_affected`, но нужен ещё один вход); low или «unknown» для записей без критичности (в spec только четыре уровня); библиотека для CVSS (новая зависимость ради одной формулы).

### 23. Оценка здоровья, счётчики, признаки breaking и команды обновления
**Контекст:** spec 7.1–7.3 и 7.5 задают веса, счётчики, признаки breaking и формат команд, но не говорят, что показывать без проверенных пакетов, как считать уязвимость на нескольких пакетах, какие тексты в release notes считать признаками и как обновлять алиас.
**Решение:**
- `healthScore` (`health-score.ts`): веса и потолки в константе `SCORE_RULES` — её же покажет поповер «How it's calculated». Мажорное отставание — 6 баллов за пакет, сколько бы мажоров ни было. Deprecated — по статусу пакета (а он ставится только по последней версии, решение 21). Непроверенные пакеты не участвуют, «Partial» — если их строго больше 20%. Если не проверено ничего, `score: null`, и UI показывает «—». `breakdown` по категориям даёт число, штраф после потолка и сам потолок;
- `reportCounts` (`report-counts.ts`): плитки отставания и «Vulnerable» считаются только по проверенным пакетам, разбивка — по высшей критичности пакета. «Dependencies (N)» — все пакеты, «Vulnerabilities (N)» — сумма объединённых уязвимостей по пакетам: одна GHSA на двух пакетах даёт 2, как пункты на вкладке и штраф в оценке;
- `isPossiblyBreaking` (`breaking-changes.ts`): мажорная версия — всегда; минорная — по признакам в release notes; патчи не проверяются. Признаки: заголовок markdown или строка целиком жирным со словами breaking / removed(removals) / deprecated(deprecations) / backwards incompatible; `BREAKING CHANGE` или `BREAKING:` заглавными в любом месте; conventional commit с `!` (`feat!:`, `fix(scope)!:`). Слово «deprecated» в обычном тексте не считается;
- `updateCommands` (`update-command.ts`): `npm i` / `pnpm add` / `yarn add`, dev-зависимости — отдельной командой с `-D`, пустая группа не выводится, дубли по имени убираются. Алиас пишется как `name@npm:real@version`.
**Почему:** 100 баллов для проекта, который не удалось проверить, вводят в заблуждение. spec 7.1 штрафует «пакет с мажорным отставанием», а не каждый мажор. Счёт по парам «пакет — уязвимость» совпадает с тем, что пользователь видит в списке. spec 7.2 говорит о «разделах», поэтому слово в обычном тексте не признак, иначе любой «fix deprecated warning» помечался бы как ломающий. Без `npm:` в команде установка переименовала бы зависимость.
**Альтернативы:** оценка 100 без проверенных пакетов; штраф за каждый мажор отставания; уникальные уязвимости по всему проекту для «Vulnerabilities (N)»; поиск ключевых слов по всему тексту release notes; проверка признаков и в патчах.

### 24. Модель данных и драйвер БД
**Контекст:** нужны гостевые отчёты на 7 дней, сохранённые проекты, повторные проверки с историей (задел 1.1), запись результата каждого пакета сразу по готовности, кэш внешних API и счётчики лимита. Плюс один драйвер для Neon dev-ветки, продового Neon и Postgres в CI.
**Решение:** схема в `src/server/db/schema.ts`, миграции drizzle-kit в `drizzle/`:
- `reports` — входные данные проверки (источник, `dependencies`, записи lock-файла, предупреждения, менеджер пакетов). Отчёт либо гостевой (`expires_at`), либо принадлежит проекту (`project_id`, один отчёт на проект): CHECK требует ровно одно из двух. «Save project» проставляет `project_id` и обнуляет `expires_at`, «Replace source» обновляет отчёт проекта. Id — случайный UUID, потому что гостевой отчёт открывается по ссылке;
- `projects` — имя и владелец. FK `owner_id` на таблицу пользователей Better Auth добавится в задаче 20 вместе с ней;
- `checks` — одна проверка отчёта со статусом `running / completed / partial / cancelled / failed`. Частичный уникальный индекс не даёт запустить вторую проверку, пока идёт первая. `score` и `vulnerability_count` — снимок при завершении для дашборда и истории; страница отчёта пересчитывает их чистыми функциями по `check_packages`;
- `check_packages` — PK `(check_id, name)`, снимок входа (`type`, `specifier`) и результат: версии, отставание, статус, причина «Not checked», уязвимости после `mergeVulnerabilities` в `jsonb`. Строка появляется, когда пакет обработан: Resume проверяет пакеты отчёта без строки, Retry failed — строки с причиной сбоя источника. Снимок входа сохраняет историю после замены источника;
- `api_cache` (ключ, `jsonb`, `expires_at`) и `rate_limits` (PK `(subject, window_start)`, фиксированное окно; окончательно — в задаче 21);
- удаление каскадное: проект → отчёт → проверки → результаты.

Драйвер — `postgres` (postgres.js) через `drizzle-orm/postgres-js`, клиент создаётся лениво в `getDb()` (`src/server/db/client.ts`) с `prepare: false`. SSL берётся из `sslmode=require` в URL Neon. `drizzle.config.ts` сам загружает `.env.local` через `process.loadEnvFile`, без `dotenv`.
**Почему:** входные данные живут в отчёте, а результаты — в проверках, поэтому «Check again» и Resume не требуют повторной загрузки файла, а история не теряется. Скалярные поля результата — колонки (по ним фильтрует история и дашборд), список уязвимостей — `jsonb`: он всегда читается целиком. postgres.js работает и с Neon, и с обычным Postgres (CI, Docker) и поддерживает интерактивные транзакции. `prepare: false` нужен для pooled URL Neon (PgBouncer в режиме transaction).
**Альтернативы:** `@neondatabase/serverless` (HTTP без интерактивных транзакций, не подключается к обычному Postgres без прокси); `pg` (то же, плюс `@types/pg`); отдельная таблица `project_sources` (лишний JOIN, у проекта один источник); результат пакета целиком в `jsonb` (нельзя фильтровать и сравнивать проверки в SQL).
