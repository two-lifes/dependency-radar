# Dependency Radar — техническое задание (функциональное)

Версия 1.2 · 19.10.2026 · Автор: Павел

Экраны, маршруты и навигация описаны в `screens.md` (эталон для разработки). При расхождении действует `screens.md`.

Документ описывает, **что** делает продукт и **как он ведёт себя для пользователя**. Выбор технологий, архитектура и устройство хранения данных в документ не входят и решаются отдельно.

---

## 1. Назначение продукта

Dependency Radar — веб-сервис, который показывает состояние зависимостей JavaScript/TypeScript-проекта и помогает спланировать их обновление.

Проблема, которую решает продукт: в любом фронтенд-проекте десятки и сотни пакетов. Они устаревают, в них находят уязвимости, а мажорные версии ломают обратную совместимость. Чтобы понять, что обновлять в первую очередь и чем это грозит, разработчику приходится вручную открывать страницы пакетов, читать changelog и искать информацию об уязвимостях. Dependency Radar собирает всё это на одном экране и выдаёт понятный план действий.

## 2. Целевая аудитория

| Пользователь | Задача |
|---|---|
| Фронтенд-разработчик | Быстро понять, что в проекте устарело и что можно безопасно обновить прямо сейчас |
| Техлид | Видеть состояние зависимостей во всех проектах команды и планировать работу по обновлениям |
| Рекрутер или техлид, смотрящий портфолио | Зайти в демо за один клик и за минуту понять, что умеет продукт |

## 3. Термины

- **Проект** — набор зависимостей, загруженный из файла `package.json` или из публичного репозитория.
- **Зависимость** — пакет, указанный в проекте, вместе с версией или диапазоном версий.
- **Текущая версия** — версия, которая фактически используется в проекте (по lock-файлу, если он загружен; иначе — максимальная версия, подходящая под указанный диапазон).
- **Последняя версия** — последняя стабильная опубликованная версия пакета.
- **Отставание** — разница между текущей и последней версией: патч, минорная или мажорная.
- **Уязвимость** — опубликованная запись о проблеме безопасности, затрагивающая текущую версию пакета.
- **Breaking change** — изменение в новой версии пакета, которое может сломать проект при обновлении.
- **Здоровье проекта** — итоговая оценка от 0 до 100, которая учитывает отставание и уязвимости.
- **План обновления** — упорядоченный список рекомендуемых шагов обновления.

## 4. Роли и доступ

| Роль | Возможности |
|---|---|
| Гость | Проверить один `package.json` без регистрации. Результат не сохраняется, но им можно поделиться по временной ссылке, которая живёт 7 дней |
| Пользователь | Всё, что может гость, плюс сохранённые проекты, история проверок, уведомления и настройки |
| Владелец команды | Создаёт команду, приглашает участников, управляет проектами команды |
| Участник команды | Видит проекты команды, может запускать проверки и отмечать пакеты, но не удаляет проекты и не управляет участниками |
| Демо-аккаунт | Вход одной кнопкой, заранее заполненные проекты. Изменения сбрасываются раз в сутки |

Вход: по email (ссылка для входа) или через GitHub.

## 5. Пользовательские сценарии

### 5.1. Быстрая проверка без регистрации
1. Гость открывает главную страницу.
2. Вставляет содержимое `package.json` в поле, перетаскивает файл или вводит ссылку на публичный репозиторий GitHub.
3. Нажимает «Проверить».
4. Сразу попадает на страницу отчёта. Отчёт заполняется по мере проверки: в шапке прогресс «Checked 34 of 112», строки таблицы появляются по мере готовности.
5. По окончании видит оценку здоровья, сводку и таблицу зависимостей.
6. Может скопировать ссылку на отчёт или нажать «Save project». Если он не вошёл, то после входа проект сохраняется автоматически и пользователь возвращается к нему.

### 5.2. Сохранение и регулярный мониторинг
1. Пользователь добавляет проект: даёт ему имя и выбирает источник (файл или репозиторий).
2. Выбирает частоту автоматической проверки: ежедневно, еженедельно или вручную.
3. Сервис проверяет проект по расписанию и сохраняет историю.
4. Если появилась новая уязвимость или вышла мажорная версия важного пакета, пользователь получает уведомление.

### 5.3. Планирование обновления
1. Пользователь открывает проект и переходит во вкладку «План обновления».
2. Видит шаги, сгруппированные по риску: «безопасно сейчас», «требует проверки», «мажорное обновление».
3. Для каждого шага видит, какие пакеты обновляются, до какой версии, и краткое описание breaking changes.
4. Отмечает шаги выполненными или откладывает пакет с комментарием.
5. Копирует готовую команду обновления для выбранных пакетов.

### 5.4. Разбор конкретного пакета
1. Пользователь кликает по пакету в таблице.
2. Открывается карточка пакета: версии, даты выхода, уязвимости, список изменений между текущей и последней версией.
3. Пользователь читает release notes и решает, обновлять ли пакет.

### 5.5. Работа в команде
1. Владелец создаёт команду и приглашает участников по email.
2. Участники видят общий дашборд проектов команды.
3. Участник откладывает пакет с комментарием, и остальные видят, кто и почему это сделал.

### 5.6. Просмотр портфолио
1. Посетитель открывает сайт и нажимает «Попробовать демо».
2. Сразу попадает на дашборд с 3–4 заполненными проектами разного состояния.
3. Может пройти все основные сценарии, ничего не настраивая.

## 6. Экраны и функциональные требования

### 6.1. Главная страница (лендинг)
- Заголовок с ценностью продукта одной фразой.
- Поле быстрой проверки: вставка текста, загрузка файла перетаскиванием, ввод ссылки на репозиторий.
- Кнопки «Попробовать демо» и «Войти».
- Блок «Как это работает» из трёх шагов.
- Пример отчёта (статичный скриншот или живой мини-отчёт).

### 6.2. Проверка внутри отчёта (отдельного экрана нет)
- Отдельной страницы прогресса нет: проверка идёт на странице отчёта.
- Индикатор прогресса в шапке отчёта: «Checked 34 of 112».
- Результаты появляются по мере готовности, не дожидаясь конца проверки; непроверенные пакеты показаны скелетон-строками.
- При повторной проверке сохранённого проекта видны данные прошлой проверки, а новые значения заменяют их по мере готовности.
- Кнопка отмены.
- Если часть пакетов не удалось проверить, отчёт всё равно строится, а такие пакеты помечаются с понятной причиной.

### 6.3. Отчёт по проекту
Шапка:
- имя проекта, источник, дата последней проверки, кнопка «Проверить снова»;
- оценка здоровья 0–100 с цветом (зелёный, жёлтый, красный) и пояснением, из чего она сложилась;
- сводка-счётчики: актуальных, с патч-, минорным и мажорным отставанием, с уязвимостями (по уровням критичности; правила подсчёта — раздел 7.3). Отдельного счётчика «всего пакетов» нет: общее число показывается в названии вкладки «Dependencies (112)».

Вкладки:
1. **Зависимости** (таблица, раздел 6.4).
2. **Уязвимости** — только пакеты с уязвимостями, отсортированные по критичности.
3. [1.1] **План обновления** (раздел 6.6).
4. [1.1] **История** (раздел 6.7).

### 6.4. Таблица зависимостей
Колонки: пакет, тип (основная или dev-зависимость), текущая версия, последняя версия, отставание, уязвимости, дата последнего релиза, статус (активен, давно не обновлялся, помечен устаревшим автором, не проверен).

Возможности:
- поиск по имени;
- фильтры по типу, отставанию, наличию уязвимостей, статусу (включая «не проверен»);
- сортировка по колонкам Package, Behind, Vulnerabilities, Released;
- фильтры, сортировка и поиск сохраняются в адресе страницы, чтобы ссылка открывала ту же выборку;
- массовое выделение пакетов с действием «Copy update command» (раздел 7.5); [1.1] действия «Добавить в план» и «Отложить»;
- таблица остаётся отзывчивой при 500+ пакетах.

### 6.5. Карточка пакета
Открывается боковой панелью поверх таблицы и имеет собственный адрес.
- Название, описание, ссылки на страницу пакета и репозиторий, лицензия.
- Текущая и последняя версия, временная шкала релизов между ними.
- Уязвимости: идентификатор, критичность, краткое описание, версия, в которой исправлено.
- Release notes всех версий между текущей и последней, свёрнутые по умолчанию. Версии с breaking changes визуально выделены.
- Действия: «Copy update command» (раздел 7.5); [1.1] «Добавить в план», «Отложить до…» (дата или следующая мажорная версия) с комментарием, «Игнорировать уязвимость» с обязательной причиной.

### 6.6. План обновления
- Автоматически сформированные группы:
  1. **Безопасно сейчас** — патч- и минорные обновления без известных breaking changes.
  2. **Срочно** — обновления, закрывающие уязвимости, отсортированные по критичности.
  3. **Требует проверки** — минорные обновления, в release notes которых найдены признаки ломающих изменений.
  4. **Мажорные обновления** — по одному пакету на шаг, с выжимкой изменений.
- Связанные пакеты (например, семейство одного фреймворка) объединяются в один шаг.
- У каждого шага: список пакетов «с какой на какую версию», оценка риска, кнопка копирования команды обновления, отметка «Выполнено».
- Прогресс плана: «Выполнено 5 из 12 шагов».
- Экспорт плана в Markdown (например, для задачи в трекере).

### 6.7. История проекта
- График оценки здоровья и количества уязвимостей во времени.
- Список проверок с датой и краткими изменениями: «+2 уязвимости, 3 пакета обновлено».
- Сравнение двух проверок: что добавилось, что удалено, что обновлено.

### 6.8. Дашборд (список проектов)

В MVP входит простая версия: список карточек (имя, оценка, уязвимости, дата проверки), кнопка «New project», пустое состояние. Мини-графики, переключатель «Мои / Команда» и сводный блок появляются в 1.1–1.2.
- Карточки проектов: имя, оценка здоровья, число уязвимостей, дата последней проверки, мини-график динамики.
- Переключатель «Мои / Команда».
- Сортировка по здоровью, имени или дате, поиск.
- Сводный блок по всем проектам: пакеты, которые встречаются в нескольких проектах и устарели везде.

### 6.9. Уведомления
- Внутри приложения: значок с количеством непрочитанных и список событий.
- По email: еженедельный дайджест и мгновенное письмо при появлении критической уязвимости. Каждый тип можно отключить.
- События: новая уязвимость, вышла мажорная версия отслеживаемого пакета, срок откладывания пакета истёк, проверка не удалась.
- Пользователь может «подписаться» на отдельный пакет, чтобы узнавать о любых его релизах.

### 6.10. Настройки
- Профиль: имя, email, подключённый GitHub.
- [1.2] Уведомления: какие события, каким каналом, как часто.
- [1.2] Команда: участники, приглашения, роли, удаление.
- Проект: имя, источник, [1.2] частота проверок, [1.1] игнорируемые пакеты, удаление проекта с подтверждением.
- Тема оформления: светлая, тёмная или как в системе.

## 7. Правила расчёта

### 7.1. Оценка здоровья
- Начальное значение — 100 баллов.
- Стартовые штрафы и потолок для каждой категории:

| За что | Штраф | Потолок |
|---|---|---|
| пакет с мажорным отставанием | 6 | 36 |
| пакет с минорным отставанием | 2 | 16 |
| пакет с патч-отставанием | 0.5 | 6 |
| пакет, помеченный автором как устаревший (deprecated) | 5 | 15 |
| уязвимость critical / high / moderate / low | 20 / 10 / 4 / 1 | 60 на все уязвимости вместе |

- Штраф за уязвимости начисляется за каждую уязвимость. Записи OSV, связанные через `aliases` (например, GHSA и CVE одной проблемы), считаются одной уязвимостью.

- [1.1] Отложенные и проигнорированные пакеты получают половину штрафа.
- Непроверенные пакеты в оценке не участвуют. Если не проверено больше 20% пакетов, рядом с оценкой показывается подпись «Partial».
- Итог округляется до целого, минимум 0 баллов. Цвет: 80–100 зелёный, 50–79 жёлтый, ниже 50 красный.
- Веса показываются пользователю в подсказке «Как считается оценка».

### 7.2. Определение breaking changes
- Мажорная версия всегда считается потенциально ломающей.
- В минорных версиях release notes проверяются на ключевые признаки: разделы «Breaking», «BREAKING CHANGE», «Removed», «Deprecated» и подобные.
- Пользователь видит, что это автоматическая оценка, а не гарантия.

### 7.3. Счётчики и отставание
- Плитка «Vulnerable» в сводке — число пакетов, у которых есть хотя бы одна уязвимость. Разбивка под числом (critical/high) считается по высшей критичности пакета.
- «Vulnerabilities (N)» в названии вкладки и число в колонке таблицы — количество уникальных уязвимостей: записи OSV, связанные через `aliases` (например, GHSA и CVE одной проблемы), объединяются в одну уязвимость. Тот же объединённый список используется в оценке здоровья (7.1), в счётчиках, в таблице и в карточке пакета. Объединение транзитивное: если A связана с B, а B с C, это одна уязвимость.
- У объединённой уязвимости критичность — высшая из объединённых записей. «Fixed in» — наименьшая версия, которая считается исправленной по всем объединённым записям сразу (а не минимум из их версий исправления). Если такой версии нет хотя бы по одной записи, показывается «No fix available».
- Отставание считается до последней стабильной версии (тег `latest`), пререлизы игнорируются.

### 7.4. Зависимости не из npm-реестра
- Спецификаторы `git+…`, `github:…`, `file:…`, `link:…`, `workspace:…` и ссылки на tarball не проверяются: статус «Not checked», причина «Not from npm registry». В оценке такие пакеты не участвуют.
- Алиасы `npm:<имя>@<версия>` проверяются по настоящему имени пакета.
- Теги (`latest`, `next` и другие) разрешаются в версию, на которую указывает тег.

### 7.5. Команда обновления
- Рядом с кнопкой копирования есть переключатель менеджера пакетов: npm / pnpm / yarn.
- Менеджер по умолчанию определяется по порядку: поле `packageManager` в `package.json` → наличие `pnpm-lock.yaml` / `yarn.lock` в репозитории → npm.
- Пользователь может переопределить выбор переключателем; выбор запоминается в браузере.
- Форматы: `npm i`, `pnpm add`, `yarn add`. Dev-зависимости выносятся в отдельную команду с флагом `-D`.

## 8. Состояния интерфейса

Для каждого экрана должны быть описаны и реализованы:
- **Загрузка** — скелетоны вместо пустого экрана.
- **Пусто** — понятный текст и действие (например, «Нет проектов. Добавьте первый»).
- **Ошибка** — что случилось простыми словами и кнопка «Повторить».
- **Частичный результат** — часть данных недоступна, а остальное показывается.
- **Офлайн** — сообщение о потере соединения; уже загруженные данные остаются видны.

Типовые ошибки ввода и их сообщения:
- файл не является корректным `package.json`;
- в файле нет зависимостей;
- репозиторий не найден, приватный или в нём нет `package.json`;
- внешний источник данных временно недоступен или превышен лимит запросов (с указанием, когда можно повторить).

## 9. Общие требования к качеству

- **Скорость:** первый экран отчёта появляется быстро, проверка проекта на 100 пакетов занимает не дольше 30 секунд. Повторная проверка в течение часа использует уже полученные данные.
- **Адаптивность:** всеми функциями можно пользоваться на телефоне; таблица на узком экране превращается в список карточек.
- **Доступность:** всё управляется с клавиатуры, есть видимый фокус, достаточный контраст, подписи для экранных читалок, учитывается настройка «уменьшить движение».
- **Язык интерфейса:** английский (продукт для портфолио и международной аудитории); заложена возможность добавить русский.
- **Безопасность:** сервис читает только публичные данные; загруженные файлы используются только для проверки; гостевые отчёты удаляются через 7 дней.
- **Надёжность:** сбой одного внешнего источника не ломает отчёт целиком.
- **Ограничения нагрузки:** гость — не больше 10 проверок в час с одного IP и не больше 300 зависимостей в одной проверке; вошедший пользователь — не больше 30 проверок в час. Счётчики хранятся в основной БД. Сообщения: «Too many checks. Try again in N minutes.», «Too many dependencies (max 300).»

## 10. Что не входит в первую версию

- Приватные репозитории.
- Экосистемы кроме npm (Python, PHP и т. п.).
- Автоматическое создание pull request с обновлениями.
- Мобильное приложение.
- Платные тарифы и оплата.

## 12. Критерии приёмки MVP

- [ ] Гость вставляет `package.json` из реального проекта на 100+ пакетов и получает отчёт меньше чем за 30 секунд.
- [ ] Отчёт верно показывает текущую и последнюю версию для выборочно проверенных вручную 10 пакетов.
- [ ] Пакет с известной уязвимостью (проверяется на заведомо старой версии популярного пакета) отображается с уязвимостью и версией исправления.
- [ ] Ссылка с фильтрами таблицы, открытая в другом браузере, показывает ту же выборку.
- [ ] Демо-аккаунт открывается одним кликом без ввода данных.
- [ ] Все экраны корректно работают на ширине 375 px.
- [ ] Все сценарии MVP проходятся только с клавиатуры.
- [ ] Для каждой ошибки из раздела 8 показывается понятное сообщение.
